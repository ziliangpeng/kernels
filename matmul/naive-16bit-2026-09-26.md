**Date**: 2026-09-26
**Kernel**: `matmul/matmul_naive_typed.cu` (methods `naive_f16` / `naive_bf16`)
**GPU**: H100 80GB HBM3 (a-h100-cluster, SM90) — node from Slurm job 219168
**Semantics**: A/B stored as FP16 or BF16, converted to float at load, **FP32
accumulation**. Conversion runs once (lazy, first execute) and lands in the
harness's warmup — the timed region is pure GEMM at 16-bit storage.
**Baseline**: `naive` (FP32) from the same binary + session.
**Timing**: repo-standard 100-iteration batched event timing.

## Results (square GEMM, TFLOPS)

| N | naive FP32 | naive FP16 | naive BF16 | FP16/FP32 |
|---:|---:|---:|---:|---:|
| 256 | 3.16 | 2.12 | 2.18 | 0.67x |
| 512 | 4.66 | 3.96 | 3.98 | 0.85x |
| 768 | 4.98 | 3.98 | 3.95 | 0.80x |

Verification: `naive_f16` max rel err 6.6e-05 (threshold 5e-3); `naive_bf16`
max rel err 5.6e-04 (threshold 2e-2) — both PASS; errors are pure input
quantization, as expected.

## The headline: 16-bit is SLOWER on the naive kernel (0.67–0.85x)

This is the teaching moment of the rung. Why precision reduction gains
nothing here:

1. **The naive kernel is not bandwidth-bound.** Its bottleneck is instruction
   issue + memory latency: every thread executes N iterations of (2 scalar
   loads + 1 FMA). Load:FMA = 2:1 by instruction count.
2. **Scalar 16-bit loads move the same instruction count.** One `ld.global`
   fetches one element whether it's 32-bit or 16-bit — the register is
   32-bit either way. Halving bytes-per-element halves DRAM traffic, but DRAM
   traffic isn't the constraint at these sizes.
3. **Conversion is pure overhead.** Every element passes through
   `to_float()` (cvt instruction) before the FMA — extra instructions for
   zero benefit.

FP16 and BF16 are performance-identical (within noise), confirming the
mechanism: with FP32 accumulation, the arithmetic path is the same; only the
storage format differs, and storage isn't the bottleneck.

Small-N makes it worse (0.67x at N=256): fewer FMA instructions per conversion
pair, so the cvt overhead amortizes worse.

## Prediction for the ladder (to be tested as each rung gets 16-bit)

- `smem` / `1d_blocktile` / `2d_blocktile`: still GMEM-traffic-heavy per FLOP;
  16-bit storage halves that traffic → expect **>1.0x crossover** somewhere
  here.
- `vectorized` (float4 loads): 16-bit packed as 8-element vectors halves
  load *instructions* too → biggest structural win.
- `warptile_dbuf`: already compute-bound at 37.6T (72% of cuBLAS) → 16-bit
  gains will be modest; the real unlock for 16-bit is Tensor Core WGMMA.

## Implementation notes

- `dtype_traits.h`: `DTypeTraitsHalf/Bf16` (from_float/to_float, `__host__
  __device__`), converter kernel declared in header, defined in .cu.
- `matmul_naive_typed.cu`: naive kernel templated on storage type; identical
  thread mapping to `matmul_naive.cu`; lazy one-time conversion (fixes the old
  WMMA benchmark flaw where conversion was timed with the kernel).
- Verify thresholds now per-storage-class: 1e-4 FP32, 5e-3 FP16, 2e-2 BF16.
