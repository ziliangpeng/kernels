# v9.14 worklog — multicast in the 128x128 geometry (2026-10-02)

## Design (first attempt)

NCU evidence said 128x256 has no L2 disease for multicast to treat (L2 58-68%, not
bottleneck); CUTLASS's 743.2T winner is 128x128x64 cluster 2x1 6-stage. v9_14 =
v9_13's multicast machinery transplanted to 128x128:

- CTA 128x128, 384 threads (1 producer WG + 2 consumer WGs), m64n128k16 consumers
- cluster 2 along M: CTA pair shares one B tile (128 n-cols); B split-issue
  multicast (rank r issues n-box r, mask 0x3)
- STAGES=6 (192KB), symmetric barrier ledger from v9_13
- Traffic/CTA/lap: A 16KB unicast + B 8KB issued (16KB delivered) = 24KB for
  512K FLOP = AI 21 FLOP/B issued... but multicast halves the CLUSTER's B traffic:
  cluster total 2x16(A) + 16(B) = 48KB for 1M FLOP = AI 21.3 -> effective 42.7
  counting delivery. Rationale: 2x CTAs of the 128x256 design -> better hiding.

## NCU diagnosis (v9_14 @8192)

- tensor pipe 69.4%, memory 71.3%, L2 71.2%, DRAM n/a — BOTH pipes ~70%, neither
  saturated = classic ISSUE-LIMITED signature.
- WarpState: barrier 3.87, wait 1.51, selected 1.00, long_scoreboard 0.95,
  gmma 0.93, math_pipe_throttle 0.18.
- Occupancy: 12 warps/SM (1 CTA of 384) = 2 consumer warps per SM scheduler.

## Root cause analysis

m64n128k16 retires HALF the FLOP per instruction of m64n256k16. With the same
2-consumer-WG structure, per-FLOP instruction count doubles -> the issue path
(wgmma issue + commit + wait + mbarrier handoff) becomes the bottleneck before
either tensor or memory saturates. The 128x128 geometry's higher L2 traffic
(multicast was supposed to treat it) never got the chance to bind: we are
compute-issue-limited first.

CUTLASS's 743T at the same nominal tile likely differs in warp organization
(e.g. its 128x128 kernel is likely 1 producer + 2 consumers with m64n64 macros
x2 per consumer, or uses different accumulator distribution) — worth a source
read before iterating further.

## Candidate next steps

(a) 256x128 "tall tile": 4 consumer WGs (512 thr), m64n128 each, tile 256x128,
    cluster pair shares B -> same AI as 128x256, half the instructions of v9_14.
    This keeps multicast B-sharing AND restores m64-per-WG work density.
(b) Read CUTLASS sm90 128x128 kernel source (pod has no cutlass clone; gcp5 has
    ~/cutlass) for its warp layout.
(c) Give up on 128x128: declare 128x256 no-cluster the design point (Fable's
    "the disease multicast treats doesn't exist at 128x256" + v9_12/13/14 all
    flat-or-worse = three independent confirmations).
