# WGMMA v9 — TMA + SWIZZLE_128B (2026-09-29)

## Result (job 221209, node h100-0-58)

**305.02T @ N=4096, verify PASSED (6.87e-05)** — vs v6/v7 ~163T: +87%.
The single biggest jump of the TC family. cuBLAS FP16 (728.7T) is now at
42%; WGMMA dense peak (989.4T) at 31%.

| ver | feeding | TFLOPS |
|---|---|---:|
| v6/v7 | per-thread cp.async 16B | ~163 |
| v8/v8.1 | warp-spec cp.async | 150 / 146 |
| **v9** | **TMA bulk + SWIZZLE_128B** | **305** |

## Design

Same warp-spec skeleton as v8 (producer wg + 2 consumer m64n256k16 wgs),
but the producer issues 6 TMA instructions per 64-k stage (2 A boxes + 4 B
boxes) instead of 768 per-thread 16B cp.async. TMA writes the async proxy
directly — mbarrier complete_tx orders against wgmma reads; no
fence.proxy.async, no per-thread waits. 2-stage, 96KB dynamic SMEM.

## Descriptor truth (sweep-verified, wgmma_tma_sweep.cu)

TMA SWIZZLE_128B and wgmma 128B-swizzle descriptors are designed as a pair:
one TMA box load writes the exact layout the descriptor expects.
swizzle mode = 128B (desc bits 63-62 = 01), LBO = 1 (assumed), SBO = 1024.
Sweep: 5 PASS combos, ALL at SBO=1024, LBO irrelevant — maxrel 0.000e+00.

## Bug chain (3 rounds)

1. Dynamic SMEM base only 16B-aligned; SWIZZLE_128B TMA dst must be
   1024B-aligned (the sweep's static __align__(1024) hid this). Manual
   alignment. [did not fix verify alone]
2. TMA x coordinate (inner dim = k) hardcoded 0 — every stage loaded
   k=0..63 and the K loop accumulated the same slice N/64 times. Signature:
   maxrel ~0.5 with correct magnitude = wrong accumulation. x=k0.
3. (build) m64n256 f32 requires the explicit scale-d asm operand (131
   operands); folding it to an immediate ptxas-rejects.

## What's left to cuBLAS (728.7T)

- 2-stage depth (TMA in flight ~2 stages; 3-4 needs 144KB+ > 100KB SMEM
  carveout -> smaller B tile or 128x128 CTA with 4 stages)
- consumer wait<0> after each 64-k stage (4 wgmmas) — overlap restore next
- k-major 64-k boxes mean A-tile GMEM reads are non-contiguous per box row
  (stride N) — L2-friendly CTA swizzle (threadblock swizzling) would help

## v9.1 addendum (job 221266, node h100-0-5)

**253.15T PASS (7.91e-05)** — v9 + overlap + 3-stage but CTA 128x128:
-52T vs v9. Negative result, two confounded causes: tile AI 85.3 -> 64
(more GMEM traffic per FLOP) and m64n128 wgmma less efficient per
instruction than m64n256. The overlap gain (if any) was swamped.
KEY discovery: H100 per-block opt-in SMEM is 227KB, not 100KB — we have
been needlessly capping at 100KB. v9's 128x256 shape with 3 stages
(3 x 48KB = 144KB) FITS. That is the clean single-variable experiment:
same shape as v9, only deeper pipeline + overlap restored.

## v9.2 addendum (job 221288, node h100-0-29)

**311.42T PASS (7.46e-05)** — v9 shape + 3-stage 144KB + consumer overlap
(227KB opt-in): only +6.4T (+2%) over v9's 305T. Single-variable verdict:
the 128x256 shape was already near-saturated at 2-stage; pipeline depth and
wgmma overlap are NOT the remaining bottleneck. Suspects, in order:
1. CTA wave quantization: grid 32x16 = 512 CTAs / 132 SMs = 3.88 waves —
   the tail wave runs at ~25% occupancy.
2. L2 reuse: natural rasterization walks N; A tiles re-fetched per column
   (threadblock swizzle would fix).
3. TMA issue rate: 6 boxes x 64 laps = 384 bulk copies per CTA, serialized
   behind one thread.

## v9.3 addendum (jobs 221387 + 221390 N-sweep, node h100-0-5)

**N=4096: 309.49T PASS — flat (-1.9T). But the N-sweep unmasked it:**

| N | v9.2 | v9.3 | Δ |
|---|---:|---:|---:|
| 1024 | 61.0T | 59.2T | -1.8 |
| 1536 | 123.3T | 121.3T | -2.0 |
| 2048 | 193.9T | 195.2T | +1.3 |
| 2048 note | working set 48MB ≤ L2 50MB: swizzle flat — inside L2 there is nothing to save |
| 3072 | 228.7T | 228.0T | -0.7 |
| 4096 | 312.2T | 308.1T | -4.1 (tail wave) |
| 6144 | 384.1T | 395.2T | **+11.1** |
| 8192 | 426.8T | **452.4T** | **+25.6 (+6.0%)** |

1. N=4096 was a trap: 512 CTAs / 132 SMs = 3.88 waves (tail wave ~25%
   occupancy) PARTIALLY masks the L2 effect. N-sweep is the honest probe.
2. swizzle hypothesis CONFIRMED at scale: +25.6T at N=8192 (working set
   196MB > 50MB L2), textbook L2-reuse signature (flat inside L2, gain
   beyond it).
3. cuBLAS FP16 same-N reference: 716.6 / 760.4 / 762.0T — our kernel
   reaches 59% of cuBLAS at 8192 (was 42% at 4096).
4. ncu blocked by cluster perms (ERR_NVGPUCTRPERM, needs root; shared
   cluster — not touching). N-sweep = zero-perm discriminator that worked.

Verdict: v9.3 = new champion shape going forward (v9.3 ≥ v9.2 everywhere
beyond L2; equal within noise below). Rasterization order matters at scale.

## v9.4-v9.7: three parallel ideas (jobs 221394 + 221396, node h100-0-5)

| variant | @4096 | @6144 | @8192 | verdict |
|---|---:|---:|---:|---|
| v9.3 (band swizzle, base) | 309.5 | 395.2 | 452.4 | champion before |
| v9.4 (2D 8x2 rect swizzle) | FAIL* | 388.6 | 428.6 | negative: 2-col rectangles hurt B reuse |
| v9.5 (TMA epilogue) | 331.6 | 409.6 | 460.9 | WIN +22T@4096: C write amplification was real |
| v9.6 (4-stage 192KB) | 336.7 | 433.4 | 491.9 | WIN +27T@8192: TMA latency headroom pays |
| **v9.7 (v9.5 + v9.6)** | **367.1** | **460.4** | **514.8** | synergy: +57.6 vs +49.3 additive prediction |
| cuBLAS FP16 | 716.6 | 760.4 | 762.0 | v9.7 = 67.6% @8192 |

*v9.4 verify FAIL is a ragged-N bijection bug in my rect mapping (NN=2 < GN
at N=512); not worth fixing given the negative perf trend at scale.

Mechanistic read of the v9.7 synergy: the TMA epilogue converts the C
writeback from scattered 8B stores (stealing SMEM-pipeline issue slots and
LSU bandwidth during the tail) into 2 bulk-group stores issued by one
thread; 4-stage depth lets TMA fill run further ahead of wgmma drain.
Freeing issue slots + deeper prefetch compound.

## v9.8: persistent CTAs (jobs 221402 + 221404 G-sweep, node h100-0-7)

| N | v9.7 (grid) | v9.8 (persistent 132) |
|---|---:|---:|
| 4096 | 367.1 | 367.2 |
| 6144 | 460.4 | 457.3 |

NEGATIVE: wave quantization hypothesis falsified — eliminating the 3.88-wave
tail at N=4096 gained nothing, and large N lost ~6T (the double
__syncthreads epilogue guard drains the pipeline at every tile boundary;
drain cost > wave savings). G-sweep on the runtime WG_G: G=8 optimal
(504.7 @8192; G=4 -13T, G=16/32 slightly worse) — confirms the v9.3 default.

Bug chain en route (both caught before/at build): acc[64] array under the
m64n256k16 macro (silent wrong-size, register pressure exposed it first);
register allocation 168/thread needed __launch_bounds__(384,1).

Verdict: v9.7 remains champion (367/460/515). The single-kernel wave
scheduler is NOT the win the CUTLASS lore suggests at these shapes —
probably because our CTA launch overhead is already amortized over 64
k-laps of TMA work, unlike small-K shapes.
