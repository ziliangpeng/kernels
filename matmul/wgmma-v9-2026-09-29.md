# WGMMA v9 — TMA + SWIZZLE_128B (2026-09-29)

## Result (job 221209, node h100-0-58)

**305.02T @ N=4096, verify PASSED (6.87e-05)** — vs v6/v7 ~163T: +87%.
The single biggest jump of the TC family. cuBLAS FP16 (728.7T) is now at
42%; WGMMA dense peak (989.4T) at 31%.

| ver | feeding | TFLOPS |
|---|---|---:|
| v6/v7 | per-thread cp.async 16B | ~163 |
| v8/v8.1 | warp-spec cp.async | 150 / 146 |
| **v9** | **TMA bulk + SWIZZLE_128B** | **305** |

## Design

Same warp-spec skeleton as v8 (producer wg + 2 consumer m64n256k16 wgs),
but the producer issues 6 TMA instructions per 64-k stage (2 A boxes + 4 B
boxes) instead of 768 per-thread 16B cp.async. TMA writes the async proxy
directly — mbarrier complete_tx orders against wgmma reads; no
fence.proxy.async, no per-thread waits. 2-stage, 96KB dynamic SMEM.

## Descriptor truth (sweep-verified, wgmma_tma_sweep.cu)

TMA SWIZZLE_128B and wgmma 128B-swizzle descriptors are designed as a pair:
one TMA box load writes the exact layout the descriptor expects.
swizzle mode = 128B (desc bits 63-62 = 01), LBO = 1 (assumed), SBO = 1024.
Sweep: 5 PASS combos, ALL at SBO=1024, LBO irrelevant — maxrel 0.000e+00.

## Bug chain (3 rounds)

1. Dynamic SMEM base only 16B-aligned; SWIZZLE_128B TMA dst must be
   1024B-aligned (the sweep's static __align__(1024) hid this). Manual
   alignment. [did not fix verify alone]
2. TMA x coordinate (inner dim = k) hardcoded 0 — every stage loaded
   k=0..63 and the K loop accumulated the same slice N/64 times. Signature:
   maxrel ~0.5 with correct magnitude = wrong accumulation. x=k0.
3. (build) m64n256 f32 requires the explicit scale-d asm operand (131
   operands); folding it to an immediate ptxas-rejects.

## What's left to cuBLAS (728.7T)

- 2-stage depth (TMA in flight ~2 stages; 3-4 needs 144KB+ > 100KB SMEM
  carveout -> smaller B tile or 128x128 CTA with 4 stages)
- consumer wait<0> after each 64-k stage (4 wgmmas) — overlap restore next
- k-major 64-k boxes mean A-tile GMEM reads are non-contiguous per box row
  (stride N) — L2-friendly CTA swizzle (threadblock swizzling) would help

## v9.1 addendum (job 221266, node h100-0-5)

**253.15T PASS (7.91e-05)** — v9 + overlap + 3-stage but CTA 128x128:
-52T vs v9. Negative result, two confounded causes: tile AI 85.3 -> 64
(more GMEM traffic per FLOP) and m64n128 wgmma less efficient per
instruction than m64n256. The overlap gain (if any) was swamped.
KEY discovery: H100 per-block opt-in SMEM is 227KB, not 100KB — we have
been needlessly capping at 100KB. v9's 128x256 shape with 3 stages
(3 x 48KB = 144KB) FITS. That is the clean single-variable experiment:
same shape as v9, only deeper pipeline + overlap restored.
