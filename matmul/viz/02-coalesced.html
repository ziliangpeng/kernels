Coalesced 访存可视化

~/code/kernels/matmul · matmul_naive.cu 与 matmul_coalesced.cu · H100 · N=4096 FP32

注意：本页的 "naive" 指的是 commit 9b2fb4d 之前的旧版 naive（threadIdx.x → col，本来就是 coalesced 的）。现在的 naive 已经改成真正 uncoalesced 的 threadIdx.x → row，见 01-naive.html。本页的数据和分析仍然适用于"16×16 与 32×32 block"以及"coalesced 与同样访存模式的 kernel"的对比。

1. 两个 kernel 的代码

两者都是"一个线程负责 C 的一个元素"。区别只在于线程编号怎么换算成 (row, col)，以及 block 的大小。

// naive：2D block，大小由 -b 决定（harness 默认 16，matmul.cpp:1136）
int row = blockIdx.y * blockDim.y + threadIdx.y;
int col = blockIdx.x * blockDim.x + threadIdx.x;
for (int k = 0; k < N; k++)
    sum += A[row * N + k] * B[k * N + col];

// coalesced：1D block，1024 个线程，BLOCKSIZE=32 写死，忽略 -b
int threadCol = threadIdx.x % 32;
int threadRow = threadIdx.x / 32;
int row = blockIdx.y * 32 + threadRow;
int col = blockIdx.x * 32 + threadCol;
for (int k = 0; k < N; k++)
    sum += A_row[k] * B_col[k * N];

2. 2D 线程怎样分组成 warp

硬件先把 block 里的线程拉平成一维编号，再每 32 个一组成为一个 warp：

linear_id = threadIdx.x + threadIdx.y * blockDim.x
warp      = linear_id / 32
blockwarp 0 包含的线程对应 C 的形状
naive 16×16(x=0..15, y=0) + (x=0..15, y=1)2 行 × 16 列
naive 32×32(x=0..31, y=0)1 行 × 32 列
coalescedthreadIdx.x = 0..31 → row 0, col 0..311 行 × 32 列

所以 coalesced 的访存模式和 naive -b 32 完全相同。naive 的代码本来就让 threadIdx.x → col，所以一开始就已经是 coalesced 的。（siboehm 博客里的 naive 故意写成 threadIdx.x → row，那个才是真正的 uncoalesced。）

3. 整个矩阵上的访存（可操作）

A 在左下，B 在右上，C 在右下：C 的每个格子，横向对着它要读的 A 那一行，纵向对着它要读的 B 那一列。矩阵缩小成 40×40，方便画出来。

C：前半 warp C：后半 warp 这一步用到 同 sector 带回来、没用到 整个循环会读

建议这样操作：

  1. 16×16、warp 0、k=0：C 上的紫色和青色是上下两行。B 那边两半 warp 读的是同一组橙色格子，A 那边是 2 个分开的格子，各自带回一整个 sector。
  2. 拖动 k：A 上的读取点往右走（A[row*N + k]），B 上的往下走（B[k*N + col]）。
  3. 勾选"显示整个 k 循环"：黄色是这个 warp 一共会读的区域。隔壁 warp、隔壁 block 也在读同样的行和列，这就是数据被重复读取的根源。
  4. 切到 32×32：一个 warp 是一整行，A 只要 1 个 sector，B 要 4 个。

4. 一个 warp、一步 k：sector 计数

内存访问以 32-byte sector 为单位，等于 8 个 float。同一个 warp 内重复的地址会被硬件合并。

16×16 时，B 的地址 B[k*N + col] 和 row 无关，所以两个半 warp 读的是同一组 64 bytes，并没有"读了两倍数据"。按单个 warp 计算，16×16 读的 sector 甚至更少（4 个对 5 个）。

5. block 层面：每 8 轮 k 从 L2 取多少

A 的一个 sector 含 8 个 float，读进 L1 后，接下来 7 轮 k 都能命中。以 8 轮 k 为单位：

16×16（256 线程）32×32（1024 线程）
A：每行 1 个 sector1632
B：一行 k 上的列24
合计 sector1836
换来的 FMA20488192
每 1000 次 FMA 需要的 sector8.84.4

block 越大，同一份数据被越多线程共用。这一点还是推断，有待 ncu 验证。

  • 32×32 比 16×16 快 15.9%。两者的 load 指令数相同（都是每轮 2 个 load 加 1 个 FMA），所以差距不大。
  • coalesced 比 naive 32×32 慢 6.8%，非常稳定。访存模式完全一样，所以差别来自编译出的指令。

7. SASS 对比：主循环（k 循环展开 16 次）

指令数差不多，coalesced 甚至少 3 条。唯一明显的差别是 load 的排列：coalesced 更早遇到第一个需要数据的 FFMA，同时在路上的 load 比较少，较难掩盖内存延迟。这是推断，需要用 ncu 的 warp stall reasons（long_scoreboard）确认。

8. 这一课的要点

  • 判断是否 coalesced，要看同一个 warp 的 32 个线程读的地址是否相邻，而 warp 是由拉平后的线程编号决定的。
  • 访存模式相同不代表性能相同，编译器的指令调度也能造成约 7% 的差距。
  • 先降低噪声再比较：10 轮交替运行，CV < 0.07%，小差距才可信。
  • 真正的问题是数据重用太低。下一课 smem tiling 会主动把数据搬进 shared memory，让整个 block 共用。
