Naive 访存可视化

~/code/kernels/matmul · matmul_naive.cu（commit 9b2fb4d 之后的版本：真正 uncoalesced）· H100 · FP32

1. 代码

一个线程负责 C 的一个元素。关键在于：threadIdx.x 被映射到 row（siboehm kernel 1 的写法）。

int row = blockIdx.x * blockDim.x + threadIdx.x;   // x → row
int col = blockIdx.y * blockDim.y + threadIdx.y;   // y → col
if (row < N && col < N) {
    float sum = 0.0f;
    for (int k = 0; k < N; k++)
        sum += A[row * N + k] * B[k * N + col];
    C[row * N + col] = sum;
}

同一个 warp 的线程编号是 threadIdx.x 连续的，所以它们的 row 连续、col 相同：

  • 读 A：A[row*N + k]，相邻线程的地址相隔 N×4 字节（N=4096 时是 16KB）。每个线程各占一个 32B sector，只用到其中 4 字节。
  • 读 B：B[k*N + col]，col 相同，所以是同一个地址，broadcast。
  • 写 C：C[row*N + col]，同样是 strided 写。

coalesced kernel 只是把映射反过来（threadIdx.x → col）：B 变成连续读取，A 变成 broadcast。

2. 整个矩阵上的访存（可操作）

A 在左下，B 在右上，C 在右下。矩阵缩小成 40×40。可以切换成 coalesced 的映射来对比。

C：这个 warp 负责的元素 这一步用到 同 sector 带回来、没用到 整个循环会读

建议这样操作：

  1. naive、32×32、warp 0、k=0：C 上的紫色是一整列（32 行 × 1 列）。A 那边第 0 列上有 32 个分散的橙色格子，每个都带回一整个 sector（灰色），用到的只有 1/8。B 只有 1 个格子。
  2. 切到 coalesced：C 上变成一整行，A 只剩 1 个格子，B 变成一排 32 个连续格子，刚好 4 个 sector、全部用到。
  3. 在 naive 下拖动 k 从 0 到 7：A 的读取点在同一批灰色 sector 里往右走。如果这些 sector 还留在 L1 cache 里，接下来 7 步就不用再去 L2 取。所以实际速度不一定慢 8 倍，要看 L1 能不能留住它们。

3. 一个 warp、一步 k：sector 计数（32×32 block）

naive（x→row）coalesced（x→col）
A：sector 数 / 用到的字节32 sectors（1024B）/ 128B1 sector（32B）/ 4B
B：sector 数 / 用到的字节1 sector（32B）/ 4B4 sectors（128B）/ 128B
合计 sector / 32 次 FMA335
取回数据的利用率132B / 1056B ≈ 12.5%132B / 160B ≈ 82.5%
按单个 warp 的一次 load 计算，naive 要多取约 6.6 倍的 sector。实际差距还取决于 L1 能留住多少 A 的 sector（见上面第 3 步）。
