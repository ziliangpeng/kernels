**Date**: 2026-09-26

**GPU**: H100 80GB HBM3 (gcp5, SM90) — Slurm jobs 219193 (build) + 219195 (data)
**Semantics**: FP16 storage (GMEM + SMEM tiles) + FP32 accumulation. Same

## Reading the data

1. **Penalty trajectory across rungs: 0.67 → 0.85 → 0.97.** Each rung up,
   GMEM traffic matters more (tiles get reused), so halving bytes recovers
   more of the cvt tax. The trend is real but the crossover hasn't happened.
2. **Why still < 1.0x — my implementation converts on the hot path.** The
   compute loop does `to_float(As[ty][k]) * to_float(Bs[k][tx])` — **2 cvt
   per FMA**, executed 32× per tile per thread. The inner loop is now
   2 SMEM loads + 2 cvt + 1 FMA = 40% more instructions than FP32, and that
   eats almost exactly the GMEM-halving win (net −3%).
3. **The obvious next experiment (load-time conversion):** convert FP16→FP32
   once when staging the GMEM→SMEM tile (1 cvt per element, each element then
   reused 32× from SMEM as FP32) → cvt per FMA drops from 2 to 2/32 ≈ 0.06.
   SMEM goes back to 8KB (same as FP32 version) but 32×32 tiles don't strain
   capacity, so occupancy is unchanged. Prediction: this variant crosses 1.0x
   if GMEM traffic is a real constraint at this rung. It isolates the
   mechanism: if load-time-conversion FP16 ≈ FP32 exactly, traffic wasn't
   binding; if it exceeds FP32, the traffic channel is real.
4. Roofline check: smem rung AI = 2·32·32/(64·4) = 8 FLOP/B → BW roof
   ≈ 3.35TB/s × 8 = 26.8T. Measured 7.1T — the rung is still latency/issue
   bound, not bandwidth bound, which is why halving traffic only pays ~3%.

## Implementation notes

- 16-bit tiles in SMEM (4KB vs 8KB) — capacity benefit unused at this tile
  size but the pattern carries to bigger-tile rungs.
- `dtype_traits.h` gained `zero()` for boundary fill.
