## Findings

1. **Same winner, same rank order, ±1.5% per config.** FP32 13.34T vs FP16
   13.24T at the shared winner (128,128,4,32) — a statistical tie. The 1D
   rung at its optimum is balanced on the edge: traffic saving ≈ cvt tax.
2. **FP16 wins where tiles are wide-and-thin (BN big, TM big):** +5.6% at
   (128,128,2,64) — configs with the highest GMEM traffic per FLOP. The
   dtype difference is only visible in the traffic-heavy corner of the
   config space, exactly where roofline says it should be.
3. **LAUNCH_FAIL is itself data:** TM≥128 needs 128+ FP32 accumulators per
   thread; with A/B staging indices the kernel exceeds 64K regs/SM and
   cannot launch. Same wall for both dtypes (accumulators are FP32 either
   way) — the register cliff is dtype-independent at this rung.
4. **Tuned vs default:** FP16 tuned 13.24T vs default-config 12.62T = +4.9%
   from autotuning; the FP32 side gets +6.2% (13.34 vs 12.51). Autotune
   gains shrink slightly under FP16 because the optimum moves toward
   configs where traffic is already amortized.

## Addendum (same day, post-warmup-fix): why FP16 tuned < FP16 default

Per-config dtype A/B (N=4096, jobs 219258/219259):

| Config | FP32 | FP16 | ratio |
|---|---:|---:|---:|
| (64,64,4,16) — FP32 winner | 19.36T | 12.46T | 0.64x |
| (64,64,8,8) — default | 17.56T | 16.03T | 0.91x |
| (32,32,4,8) — FP16 winner | ~15.4T | 16.31T | ~1.06x |

**FINAL CORRECTION (job 219273, same-node A/B)**: "FP16 tuned < not tuned"
NEVER EXISTED. It was a cross-node comparison artifact. On the SAME node
(h100-0-19): typed kernel default config 16.42T, tuned sweep same config
16.03T, sweep winner 16.31T — tuned and default are EQUAL within noise
(0.7%), and the sweep's absolute level is only 2.4% below the hard-coded
kernel (template runtime dispatch vs constants — small real codegen cost).
The earlier "17.21T default" was node h100-0-15, which runs FP16 ~7% faster
than h100-0-19 node-to-node. Prior claims in this file that "the FP16
landscape peak is genuinely lower" or "dtype optima migrate" relied on the
cross-node pair and are RETRACTED; the TM=16 cvt-tax analysis stands
(0.64x per-config same-node), but FP32-winner-TM=16 vs FP16-winner-small-TM
should be re-verified on one node before being cited.

**TM=16 is FP32's sweet spot but FP16's poison.** Every A-tile SMEM read
costs a cvt; at TM=16 the cvt:FMA ratio is ~17:16 and the wide accumulator
raises register pressure — the reuse win is fully eaten. At TM=8 the tax is
0.91x, and at (32,32,4,8) FP16 actually WINS (~1.06x): small tiles let the
halved SMEM/GMEM footprint pay. The FP16 optimum migrates to small-TM
configs whose ceiling is simply lower than FP32's big-TM optimum. "Tuned
FP16 < default FP16" is dtype-dependent optima, not autotuner failure.
