2D blocktile 可视化

~/code/kernels/matmul · matmul_2d_blocktile.cu · H100 · FP32 · 第 5 课

1. 思路：一个 thread 算一个 8×8 方块

1D blocktile 让 B 读一次、用 8 次（tmpB），但 A 还是每做一次 FMA 就从 smem 读一次。2D blocktile 让每个 thread 负责 C 里的一个 8×8 方块（TM = TN = 8），A 和 B 都先读进寄存器，再做外积：

            b0    b1   ...   b7      ← regB[8]：Bs 第 dotIdx 行里连续 8 个
     a0   a0·b0 a0·b1  ...  a0·b7
     a1   a1·b0 a1·b1  ...  a1·b7
     ..    ...
     a7   a7·b0 a7·b1  ...  a7·b7    ← 64 个格子 = threadResults[8][8]，累加
     ↑ regA[8]：As 第 dotIdx 列里的 8 个

每个 dotIdx：从 smem 读 8 + 8 = 16 个数，做 8 × 8 = 64 次 FMA。每个读进来的数用 8 次（a0 用一整行，b0 用一整列）。1D 里 B 用 8 次、A 只用 1 次。

64 个格子是部分和：K 方向一共 4096 步（512 轮 tile × 每轮 8 个 dotIdx），每一步都往这 64 个寄存器里累加，最后一次性写回 C。

相对第 4 课1D2D
smem tile、两个 __syncthreads、BK = 8、搬运/计算两套映射完全一样
① 每个 thread 的输出形状一列 8 个8×8 方块，64 个
② 内层循环B 进寄存器，A 每次读 smemA、B 都进寄存器，外积
③ 尺寸block 64×64，512 thread，每人搬 1 个block 128×128，256 thread，每人搬 4 个

③ 是被 ① 逼出来的：如果 block 还是 64×64，每个 thread 算 64 个输出，只需要 64 个 thread，太少；放大到 128×128 就是 128·128/64 = 256 个 thread。

2. 参数

参数值含义
BM × BN128 × 128一个 block 负责 C 的 128×128
BK8每轮沿 K 搬 8 列 A、8 行 B
TM × TN8 × 8每个 thread 算 64 个输出
thread 数(128/8) × (128/8) = 256排成 16 × 16 的 thread 网格
smem(1024 + 1024) × 4B = 8KBAs[128][8] + Bs[8][128]，没有 padding
寄存器源码层 80 个；SASS 实测 162 个，无 spillGPU 寄存器是 32 位、不分类型；一个 float 占 1 个。162 × 256 ≈ 41.5K > 32K → 每个 SM 只放得下 1 个 block（8 个 warp，按寄存器算，未用 ncu 测）

3. warp 和 block 在 C 里的形状

threadCol = tid % 16，threadRow = tid / 16。一个 warp 是 32 个连续 tid：前 16 个 threadRow 相同、threadCol = 0..15，后 16 个 threadRow 加 1。所以一个 warp = 2 × 16 个 thread 方块 = C 里 16 行 × 128 列的一条，一个 block 的 8 个 warp 从上到下叠成 128×128。

4. 代码（逐行注释）

__shared__ float As[128][8];             // A 的 tile，原样存（行优先）
__shared__ float Bs[8][128];

const int threadCol = threadIdx.x % 16;  // 0..15 → 负责 C 第 threadCol*8 .. +7 列
const int threadRow = threadIdx.x / 16;  // 0..15 → 负责 C 第 threadRow*8 .. +7 行
// warp 视角：threadRow 只有 2 个值，threadCol 0..15 各出现两次

A += blockRow * 128 * N;  B += blockCol * 128;  C += blockRow * 128 * N + blockCol * 128;

float threadResults[8][8] = {{0.0f}};    // 64 个累加器（寄存器）
float regA[8], regB[8];                  // 16 个输入寄存器

// 搬运映射：1024 个 A / 256 thread = 每人 4 个 → 4 轮
const int strideA = 256 / 8;   // 32：每轮往下 32 行
const int strideB = 256 / 128; // 2：每轮往下 2 行
const int innerRowA = threadIdx.x / 8,   innerColA = threadIdx.x % 8;
const int innerRowB = threadIdx.x / 128, innerColB = threadIdx.x % 128;

for (int tileIdx = 0; tileIdx < N; tileIdx += 8) {
    for (int off = 0; off < 128; off += 32)               // A：第 r, r+32, r+64, r+96 行
        As[innerRowA + off][innerColA] = A[(innerRowA + off) * N + innerColA];
        // warp：4 行 × 每行 8 个连续 float（4 个 32B sector，不是 1 条 128B line）
        // 写 smem 的地址 = tid + 常数 → 连续，无 bank conflict
    for (int off = 0; off < 8; off += 2)                  // B：第 r, r+2, r+4, r+6 行
        Bs[innerRowB + off][innerColB] = B[(innerRowB + off) * N + innerColB];
        // warp：同一行连续 32 个 float = 1 条 128B line，coalesced
    __syncthreads();
    A += 8;  B += 8 * N;

    for (int dotIdx = 0; dotIdx < 8; dotIdx++) {
        for (int i = 0; i < 8; i++) regA[i] = As[threadRow * 8 + i][dotIdx];
        // 单 thread：As 的一列，相邻相差 8 个 word
        // warp：2 个不同地址，相差 64 word → 同一个 bank → 2-way 冲突（按 32 位读取推理）
        // SASS 实测：dotIdx 展开后编译器改成 LDS.128，一次读 As[r][0..3]（4 个 dotIdx），每 tile 16 条
        for (int j = 0; j < 8; j++) regB[j] = Bs[dotIdx][threadCol * 8 + j];
        // 单 thread：连续 8 个 float
        // warp：16 个不同地址，相邻相差 8 word → 只落在 4 个 bank → 4-way（按 32 位读取推理）
        // SASS 实测：每个 dotIdx 2 条 LDS.128，每 tile 16 条
        for (int i = 0; i < 8; i++)
            for (int j = 0; j < 8; j++)
                threadResults[i][j] += regA[i] * regB[j];  // 64 次 FFMA，全在寄存器
    }
    __syncthreads();
}
for (i..8) for (j..8)                                       // 写回：每人 64 个，只写一次
    C[(threadRow * 8 + i) * N + threadCol * 8 + j] = threadResults[i][j];
    // warp：32 个 lane 落在 32 个不同 sector，每个只写 4B——差，但只发生一次

只数指令，2D 比 1D 好 4.5 倍；但算上 bank 冲突，按 wavefront 只好 1.5 倍，和实测的 1.26× 量级接近。这是推测：没看过 SASS，也没用 ncu 量 bank conflict。编译器可能把 B 的 8 个连续读合并成 LDS.128，那样 wavefront 会更少。

粗略上限（推测）：H100 每个 SM 每拍能发 4 条 warp-FFMA、处理 1 个 smem wavefront。按上表，64 条 FFMA 要 16 拍，48 个 wavefront 要 48 拍 → smem 是瓶颈，上限约 16/48 × 67T ≈ 22T，和实测 22.21T 很接近。但同一个模型套在 1D 上得 14.9T，比 1D 实测 17.56T 还低，说明编译器至少在 1D 里做了源码以外的事。所以这个"吻合"可能是巧合。

global 访问不是瓶颈（推测）：总流量约 4.3GB，按 6.2ms 算约 0.7TB/s，远低于 HBM 和 L2 的带宽。

  • As 和 Bs 都被合并成 LDS.128：每 thread 每 dotIdx 只有 4 条 smem 读，不是 16 条。As 能合并，是因为 dotIdx 循环完全展开后，As[r][0..7] 在 smem 里连续。Simon 在 A6000 上的 SASS 里 As 还是 32 位 LDS，我们的 build 不一样。
  • 上表"48 个 wavefront → smem 是瓶颈 → 上限约 22T"的推理不成立：4 条 LDS.128 就算每条 4 个 wavefront 也只有 16 个，和 64 条 FFMA 的 16 拍持平。22T 的"吻合"是巧合。1D 的 As 也被合并成了 LDS.128，这解释了同一模型为什么低估 1D。
  • 新嫌疑（推测，未测）：寄存器 162 个 → 每个 SM 只有 1 个 block，搬运（LDG 几百拍延迟）和计算被两个 __syncthreads 串起来，搬运时没有别的 block 能顶上。要用 ncu 看 occupancy 和 stall 原因才能确认。

8. 仓库文档里的问题（未修改）

  • matmul_2d_blocktile.h:22 的 "Expected ~68.7% of cuBLAS (1.9x over 1D)" 是 siboehm 的 Kernel 5 在 A6000（未调参）上的数字；本机是 42.8%、1.26×。（2026-10-03 更正：之前这里写成"A100 上自动调参"，是我说错了。）
  • RESULTS.md:82 说 As[BM][BK+1] padding "built INTO 2D/vectorized"。实际上 matmul_2d_blocktile*.cu 和 matmul_vectorized.cu 都没有 padding，只有 matmul_vectorized_auto.cu 有。
  • worklog.md Step 5 说搬 A 时 "32 threads of a warp all read the same row… coalesced 128B"。BK = 8 时一个 warp 读的是 4 行 × 8 个 float，只有 B 是同一行。
  • worklog 的 "16 SMEM reads → 64 madds" 只数了指令，没算 bank 冲突；"total reuse factor = 8 × 8 = 64" 混了概念（每个值复用 8 次，64 是 FMA 数）；"4× 1D" 实际是 4.00 / 0.89 ≈ 4.5×。
  • worklog 说自动调参类 "see matmul_2d_blocktile.cu"，实际在 matmul_2d_blocktile_auto.cu。
  • worklog 用 "likely spilling" 解释 TM/TN 不对称，没有验证。另一种推测：TN = 16 时一个 warp 跨 4 个 threadRow，As 读变成 4-way 冲突。
  • matmul_2d_blocktile_tuned.cu:128,131 的 BK = 24 配置不满足 NUM_THREADS % BK == 0，会写出 smem 边界。

9. 要点

  • 2D = 寄存器这一层两边都复用：16 次 smem 读换 64 次 FFMA，每个值用 8 次。
  • 一个 warp 在 C 里是 16 行 × 128 列的一条，一个 block 是 8 条叠起来。
  • "读几次"不等于"花几拍"：同一条指令里 32 个 lane 的地址如果挤在少数几个 bank，就要拆成多个 wavefront。按源码字面（32 位读取），2D 的 As 读是 2-way、Bs 读是 4-way。
  • 但先看 SASS：我们的 build 把 As、Bs 都编成了 LDS.128，smem 很可能不是主要瓶颈；新嫌疑是 162 个寄存器 → 每 SM 只有 1 个 block（推测）。源码字面 ≠ 实际指令。
  • 搬运阶段是干净的：A 每 warp 4 个用满的 sector，B 一条 128B line，写 smem 无冲突。
  • 同一条原则用了第三次：HBM→smem（第 3 课）、smem→寄存器只复用 B（第 4 课）、smem→寄存器 A 和 B 都复用（本课）。
