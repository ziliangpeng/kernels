1. Problem: scalar FMA instructions

So far, each thread does scalar multiply-adds: sum += a * b. One FMA instruction = 2 FLOPS (1 mul + 1 add). An H100 CUDA core can do ~2 FLOPS/cycle. With 16,896 cores: ~67 TFLOPS FP32.

But H100 has tensor cores — hardware matrix multiply units that can do D = A × B + C on 16×16×16 matrices in a single instruction. Each tensor core does 16×16×16×2 = 8192 FLOPS per instruction. H100 has 528 tensor cores → 989 TFLOPS FP16 (15× the scalar FP32 peak).

Tensor core vs scalar CUDA core: Scalar CUDA core: 1 FMA instruction → 2 FLOPS (1 mul + 1 add) Need 4096³ = 137 billion FMA instructions for a GEMM Tensor core: 1 wmma instruction → 16×16×16 matrix multiply = 8192 FLOPS Need 137B / 4096 = 33 million wmma instructions for same GEMM → 4096× fewer instructions → 15× higher throughput (989 vs 67 TFLOPS)

2. WMMA — Warp Matrix Multiply Accumulate

The wmma API provides access to tensor cores. A warp (32 threads) cooperatively loads matrix fragments, multiplies them, and stores the result.

#include <mma.h>
using namespace nvcuda;

// Define fragment types
wmma::fragment<wmma::matrix_a, 16, 16, 16, __half, wmma::row_major> a_frag;
wmma::fragment<wmma::matrix_b, 16, 16, 16, __half, wmma::col_major> b_frag;
wmma::fragment<wmma::accumulator, 16, 16, 16, float> c_frag;

// Initialize accumulator to zero
wmma::fill_fragment(c_frag, 0.0f);

for (int kt = 0; kt < K; kt += 16) {
    // Load 16×16 tiles from SMEM into fragments
    wmma::load_matrix_sync(a_frag, &As[ty][kt], 16);
    wmma::load_matrix_sync(b_frag, &Bs[kt][tx], 16);

    // Tensor core multiply-accumulate: c_frag += a_frag × b_frag
    wmma::mma_sync(c_frag, a_frag, b_frag, c_frag);
}

// Store result to global memory
wmma::store_matrix_sync(&C[row * N + col], c_frag, N, wmma::mem_row_major);

The accumulate is always FP32. Even when A and B are FP16, the multiplication is done in FP16 but accumulation in FP32 for precision. This prevents overflow and gives near-FP32 accuracy.

cuBLAS is still 10× faster than a hand-written wmma kernel. This is because cuBLAS uses CUTLASS templates with every optimization: perfect tiling, shared memory bank padding, register double buffering, async copy, TMA (Tensor Memory Accelerator), and auto-tuning. Writing a competitive GEMM is extremely hard — this is why libraries like cuBLAS/CUTLASS exist.

5. Beyond wmma: wgmma and TMA (Hopper+)

On H100 (sm_90), wgmma (warp-group MMA) replaces wmma — it operates on 4 warps (128 threads) at once, with larger tile sizes and direct global→register loads via TMA. This is the cutting edge of GEMM optimization.

🎯 Chapter 12 Summary

Tensor cores do 16×16×16 matrix multiply in one instruction = 8192 FLOPS (vs 2 for scalar FMA). Use wmma API: load_matrix_sync → mma_sync → store_matrix_sync. FP16/BF16 inputs, FP32 accumulate. 15× the FP32 throughput (989 TFLOPS FP16 on H100). cuBLAS still ~10× faster than hand-written due to CUTLASS-level optimizations. Hopper adds wgmma + TMA for even higher performance.

🧪 Quick Check

Why is cuBLAS still ~10× faster than a hand-written wmma GEMM kernel?

cuBLAS uses CUTLASS templates with every optimization stacked: perfect tile sizes for each architecture, SMEM bank conflict padding, register-level double buffering, cp.async pipelining, TMA (Tensor Memory Accelerator for Hopper), and auto-tuning across hundreds of configurations. A hand-written kernel typically gets ~10% of peak; cuBLAS gets ~90%+. This is why GEMM libraries exist — writing a competitive GEMM from scratch is months of engineering work.
