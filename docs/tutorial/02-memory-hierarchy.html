1. The full memory hierarchy

GPU memory hierarchy (H100): ┌──────────────────────────────────────────────────┐ │ Registers (per thread) ~65536 per SM │ ← 1 cycle │ ┌──────────────────────────────────────────┐ │ │ │ Shared Memory / L1 (per block) ~228KB │ │ ← 30 cycles │ │ ┌──────────────────────────────────┐ │ │ │ │ │ L2 Cache (global) ~50MB │ │ │ ← 200 cycles │ │ │ ┌──────────────────────────┐ │ │ │ │ │ │ │ Global Memory (HBM) 80GB │ │ │ │ ← 400+ cycles │ │ │ │ (3 TB/s bandwidth) │ │ │ │ │ │ │ └──────────────────────────┘ │ │ │ │ │ └──────────────────────────────────┘ │ │ │ └──────────────────────────────────────────┘ │ └──────────────────────────────────────────────────┘ Faster = smaller. Slower = bigger. The game is to keep data in the fast levels as much as possible.

2. Global memory — big but slow

Global memory is the GPU's main memory (HBM — High Bandwidth Memory). It's large (80GB on H100) and has high bandwidth (3 TB/s), but it's high latency (~400 cycles). All threads can access it, but it's the slowest memory on the GPU.

// Global memory — accessible by all threads, all blocks
__global__ void kernel(float* global_array) {
    // This load goes to global memory (unless cached in L2)
    float x = global_array[threadIdx.x];  // ~400 cycles
}
High bandwidth ≠ low latency. HBM on H100 delivers 3 TB/s — enormous throughput. But each individual load takes ~400 cycles. The GPU hides this latency by running thousands of threads: while one waits for memory, others compute. This is why you need massive parallelism.

3. Shared memory — fast but small

Shared memory (SMEM) is on-chip SRAM, shared among threads in a block. It's ~100× faster than global memory but tiny (~228KB per SM on H100). It's the programmer's responsibility to manage — you explicitly load data from global to shared, use it, then discard.

__global__ void kernel(float* global_a) {
    // Declare shared memory (per block)
    __shared__ float tile[256];

    // Thread 0..255 each load one element from global → shared
    int tid = threadIdx.x;
    tile[tid] = global_a[tid];  // global → shared (~400 cycles)

    // MUST synchronize — wait for all loads to finish
    __syncthreads();

    // Now all threads can read from shared (~30 cycles)
    float x = tile[255 - tid];  // reverse access, still fast
}
__syncthreads() is mandatory after shared memory writes. Without it, some threads might read shared memory before other threads have finished writing to it — a race condition. __syncthreads() acts as a barrier: all threads in the block wait here until all have arrived.

Bank conflicts

Shared memory is divided into 32 banks. If all 32 threads in a warp access different banks, all accesses happen in one cycle. If two threads access the same bank, they're serialized — a bank conflict.

Shared memory banks (32 banks, 4 bytes each): Bank: 0 1 2 3 4 ... 31 Addr: [0] [1] [2] [3] [4] ... [31] [32][33][34][35][36]... [63] ... No conflict: 32 threads access addresses [0..31] (one per bank) 2-way conflict: threads 0 and 1 both access bank 0 → 2 cycles Broadcast: all threads read bank 0 → 1 cycle (broadcast is free)

4. Registers — fastest, per-thread

Each thread has its own registers (~255 max per thread on H100). Register access is 1 cycle — the fastest memory. The compiler manages register allocation; you don't explicitly declare registers. But you can influence it.

__global__ void kernel() {
    // These are stored in registers (if the compiler can)
    float a = 1.0f;
    float b = 2.0f;
    float c = a + b;  // all in registers, 1 cycle

    // If you use too many, they "spill" to local memory (slow!)
    float arr[100];  // likely spills to local memory
}
Register spilling: If a kernel uses more registers than the hardware allows (255 per thread on H100), the compiler "spills" the excess to local memory — which is actually stored in global memory (slow!). Use nvcc -res-usage to check register usage per kernel.

5. L1 / L2 caches

CacheScopeSize (H100)Managed by
L1Per-SM~256KB (shared with SMEM)Hardware (automatic)
L2Global (all SMs)~50MBHardware (automatic)

L1 and L2 are hardware-managed caches — you don't control them explicitly. Global memory accesses go through L2 (and optionally L1). Repeated accesses to the same address may hit the cache, saving a trip to HBM.

L1 and Shared Memory share the same physical SRAM. On H100, you can configure the split: e.g., 128KB SMEM + 128KB L1, or 228KB SMEM + 28KB L1. More SMEM = less L1 cache and vice versa. Use cudaFuncSetAttribute to configure.

🎯 Chapter 02 Summary

Registers (1 cycle, per-thread) → Shared memory (30 cycles, per-block, programmer-managed) → L1 (30 cycles, hardware cache) → L2 (200 cycles, hardware cache) → Global HBM (400 cycles, 80GB, 3 TB/s). The key optimization in GPU kernels: move data from global to shared memory once, reuse it many times from shared. Use __syncthreads() after SMEM writes. Watch for bank conflicts and register spilling.

🧪 Quick Check

You have a 256-element array that all 256 threads in a block need to read from. Where should you put it?

Shared memory. Each thread loads one element from global to shared (one global access per element), then __syncthreads(), then all threads read from shared (30 cycles, 19 TB/s). Without shared memory, every thread would go to global memory (400 cycles) — 13× slower. This is the fundamental pattern of GPU optimization: load once to fast memory, reuse many times.
