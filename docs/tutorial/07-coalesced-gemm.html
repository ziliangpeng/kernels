1. Problem with naive GEMM's access pattern

In the naive kernel, thread (row, col) loads A[row][k] and B[k][col]. Consecutive threads in a warp have consecutive col values (same row). This means:

  • B access: B[k][col], B[k][col+1], ... → consecutive addresses → coalesced ✓
  • A access: A[row][k] for all threads → same address → broadcast (OK)

Actually, the naive kernel's coalescing isn't terrible — the real problem is the memory amplification. But there's a subtlety: as k iterates, the A access pattern is strided if threads have different rows.

2. Fix: ensure coalesced access for both A and B

The standard fix is to arrange the thread mapping so that consecutive threads access consecutive memory. The most common approach: use 2D blocks where threadIdx.x maps to columns (fastest-changing) and threadIdx.y maps to rows.

__global__ void gemm_coalesced(const float* A, const float* B, float* C,
                             int M, int N, int K) {
    // threadIdx.x → col (consecutive threads → consecutive B columns)
    // threadIdx.y → row
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;

    if (row < M && col < N) {
        float sum = 0.0f;
        for (int k = 0; k < K; k++) {
            // B[k][col] — consecutive col → coalesced ✓
            // A[row][k] — same row, same k → broadcast ✓
            sum += A[row * K + k] * B[k * N + col];
        }
        C[row * N + col] = sum;
    }
}

3. Measured improvement

KernelTFLOPS (4096³, H100)% peak
Naive (bad pattern)~0.30.4%
Coalesced~0.50.7%
The improvement is modest. Coalescing helps, but the dominant bottleneck is still memory amplification — each byte is still loaded thousands of times. Coalescing only ensures each individual load is efficient; it doesn't reduce the number of loads. The real fix is shared memory tiling (next chapter).

4. What's still wrong

Still wrong with coalesced GEMM: The k-loop still goes to global memory K times per thread. Each A[row][k] is loaded by all N threads in that row. Each B[k][col] is loaded by all M threads in that column. We need to REUSE data across threads — not just access it efficiently. Solution: load a TILE of A and B into shared memory (fast, on-chip), compute a partial result from the tile, then load the next tile. This is "shared memory tiling" — the most important GPU optimization technique.

🎯 Chapter 07 Summary

Coalesced GEMM ensures consecutive threads access consecutive memory (threadIdx.x → columns). This makes each individual load efficient, but doesn't reduce the total number of loads — memory amplification is still ~K×. The improvement is modest (~0.3 → ~0.5 TFLOPS). The real fix is shared memory tiling: load a tile of A and B into SMEM, reuse across threads.

🧪 Quick Check

Why does coalescing only give a modest improvement for GEMM?

Because the dominant bottleneck is memory amplification, not access efficiency. Coalescing ensures each load transaction is full (128B used), but each byte is still loaded ~K times (4000× for K=4096). Coalescing fixes the per-transaction efficiency but not the total traffic. Shared memory tiling (next chapter) fixes the total traffic by reusing loaded data.
