1. What is DSA?

DSA (Dynamic Sparse Attention) is the attention mechanism used in DSV4 (DeepSeek V4). It combines three sparse attention patterns to achieve O(S) complexity while maintaining long-range context. This is the end goal of your GPU kernel learning journey — writing a DSA sparse MLA decode kernel from scratch.

DSA = SWA + CSA + HCA Full attention: every token attends to every other → O(S²) DSA: three sparse patterns, each O(S): 1. SWA (Sliding Window): attend to nearby tokens (window of W) 2. CSA (Chunked Sparse): attend to anchor tokens every C positions 3. HCA (Hierarchical Context): attend to coarse summary tokens Combined: each token attends to O(W + S/C + H) others → O(S) total → enables 128K+ context without O(S²) memory/compute

2. Sliding Window Attention (SWA)

Each token attends to the W tokens before it (sliding window). This captures local context efficiently.

# SWA mask: token i attends to [max(0, i-W), i]
for i in range(S):
    for j in range(max(0, i - W), i + 1):
        mask[i][j] = True

# In kernel form: each Q row only loads K/V for [i-W, i]
# → O(W) K/V loads per token instead of O(S)

3. Chunked Sparse Attention (CSA)

Divide the sequence into chunks of size C. Each token attends to the first token of each chunk (anchor tokens). This gives long-range coverage with O(S/C) attention per token.

4. Hierarchical Context Attention (HCA)

Summarize each chunk into a single token (via pooling), then attend to all chunk summaries. This gives global context at reduced cost.

5. Multi-head Latent Attention (MLA)

MLA compresses the K and V into a low-rank latent representation, reducing KV cache size. Instead of storing (S, n_heads, d_head) for K and V, it stores (S, d_latent) where d_latent << n_heads × d_head. The K and V are reconstructed on-the-fly from the latent.

MLA + DSA is the frontier. DSV4-Flash uses MLA with DSA. The decode kernel needs to: (1) reconstruct K/V from latent, (2) apply SWA+CSA+HCA sparse masks, (3) compute attention only on the non-zero pattern. Only ~10-15 people can write this kernel from scratch — you're learning toward being one of them.

6. What the kernel needs to do

# Pseudocode for DSA sparse MLA decode kernel:
@triton.jit
def dsa_mla_decode(q_ptr, kv_latent_ptr, ...):
    pid = tl.program_id(0)

    # 1. Load Q for this head
    q = tl.load(q_ptr + ...)

    # 2. Determine sparse pattern for this position
    swa_start = max(0, pos - W)
    csa_anchors = range(0, S, C)  # first token of each chunk
    hca_summaries = range(0, S, C)  # pooled tokens

    # 3. Collect all indices this token attends to
    sparse_indices = sorted(set(
        range(swa_start, pos) |       # SWA
        csa_anchors |                  # CSA
        hca_summaries                  # HCA
    ))

    # 4. Gather K/V at sparse indices (NOT full sequence)
    k = tl.load(kv_latent_ptr + sparse_indices)  # reconstruct from latent
    v = tl.load(kv_latent_ptr + sparse_indices)

    # 5. Compute attention only on sparse subset
    scores = tl.dot(q, k.T) * scale
    # Apply causal mask + softmax
    attn = tl.softmax(scores)
    out = tl.dot(attn, v)

    tl.store(o_ptr + ..., out)
The challenge is the gather. Unlike standard attention where K/V are contiguous, sparse attention requires gathering from non-contiguous indices. This is memory-access-pattern-hard: the indices change per position, and you need to batch them efficiently. This is where Triton's block-level abstraction shines — you can load a block of sparse indices and gather in one tl.load call.

🎯 Chapter 20 Summary

DSA = SWA + CSA + HCA, three O(S) sparse attention patterns. SWA attends to W nearby tokens. CSA attends to chunk anchors (every C tokens). HCA attends to chunk summaries. MLA compresses KV into low-rank latent (d_latent << n_heads × d_head). The kernel: determine sparse pattern per position, gather K/V at sparse indices (non-contiguous), compute attention only on the subset. The gather is the hard part — non-contiguous access patterns. Only ~10-15 people can write this from scratch.

🧪 Quick Check

Why is the DSA sparse MLA kernel harder to write than a standard FlashAttention kernel?

Two reasons: (1) Sparse gather — standard FlashAttention loads K/V contiguously (coalesced). DSA must gather K/V at arbitrary sparse indices (SWA + CSA + HCA), which are non-contiguous → uncoalesced, much harder to optimize. (2) MLA reconstruction — K/V aren't stored directly, they're reconstructed from a compressed latent, adding a matmul before the attention. You must fuse the latent reconstruction, sparse gather, and attention into one kernel to avoid HBM round-trips. This is why only ~10-15 people can write it.
