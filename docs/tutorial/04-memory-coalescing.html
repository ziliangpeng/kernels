1. What is memory coalescing?

The GPU's memory controller loads data in 128-byte cache lines. When all 32 threads in a warp access consecutive addresses within the same 128-byte segment, the GPU can satisfy all 32 loads with a single memory transaction. This is a coalesced access.

Coalesced vs uncoalesced access: COALESCED (good): 32 threads access consecutive floats (4 bytes each) Thread: 0 1 2 3 ... 31 Addr: 100 104 108 112 ... 224 ───────── 128 bytes ────────── → 1 memory transaction (128 bytes loaded, all used) UNCOALESCED (bad): 32 threads access strided addresses Thread: 0 1 2 3 ... 31 Addr: 100 500 900 1300 ... (stride = 400) ├──┤ ├──┤ ├──┤ Each in a different 128B segment → 32 memory transactions (128B each, only 4B used each → 3.125% efficiency)

2. Why it matters — concrete numbers

Access patternTransactionsBandwidth usedEffective BW
Coalesced (consecutive)1128B for 128B100%
Stride-22256B for 128B50%
Stride-32324096B for 128B3.1%
Random (per-thread)324096B for 128B3.1%
Uncoalesced access can make your kernel 32× slower. The GPU still loads the full 128-byte cache line for each thread, even if only 4 bytes are used. If your kernel is memory-bound and you see low bandwidth utilization, coalescing is the first thing to check.

3. Example: coalesced vs uncoalesced matrix access

// COALESCED — each thread reads a column, threads go along a row
__global__ void read_by_row(float* mat, int W) {
    int row = blockIdx.x;
    int col = threadIdx.x;
    if (col < W) {
        float x = mat[row * W + col];  // consecutive threads → consecutive addresses ✓
    }
}

// UNCOALESCED — each thread reads a row, threads go along a column
__global__ void read_by_col(float* mat, int H, int W) {
    int col = blockIdx.x;
    int row = threadIdx.x;
    if (row < H) {
        float x = mat[row * W + col];  // consecutive threads → stride W addresses ✗
    }
}
Rule of thumb: Make sure consecutive threads (in the same warp) access consecutive memory addresses. The easiest way: have threadIdx.x correspond to the fastest-changing dimension (columns in row-major layout).

4. How to diagnose coalescing issues

# Compile with lineinfo for profiling
nvcc -O3 -lineinfo -o kernel kernel.cu

# Profile with Nsight Compute
nsys profile ./kernel
ncu --set full ./kernel

# Key metric to check:
ncu --metrics l1tex__t_sectors_pipe_lsu_mem_global_op_ld.sum     ./kernel

# If sectors/request > 1, you have uncoalesced access

🎯 Chapter 04 Summary

The GPU loads memory in 128-byte cache lines. When 32 threads in a warp access consecutive addresses, all 32 loads are served by 1 transaction (coalesced). Strided or random access → up to 32× more transactions → 32× less effective bandwidth. Rule: make threadIdx.x correspond to the fastest-changing memory dimension.

🧪 Quick Check

Your kernel reads mat[row * W + col] where row = threadIdx.x and col = blockIdx.x. Is this coalesced?

No. Consecutive threads (threadIdx.x = 0, 1, 2...) have different row values, so they access mat[0*W+col], mat[1*W+col], mat[2*W+col]... — addresses separated by W * sizeof(float) bytes. Each thread's access falls in a different 128-byte cache line → 32 transactions instead of 1. Fix: swap so col = threadIdx.x (consecutive threads → consecutive columns → consecutive addresses).
