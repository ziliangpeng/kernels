1. CPU vs GPU — why they're different

A CPU is designed for low latency — it has a few powerful cores with deep cache hierarchies and branch prediction, optimized to execute sequential code as fast as possible. A GPU is designed for high throughput — it has thousands of simple cores that work in parallel, optimized to do the same operation on lots of data simultaneously.

CPU (e.g. EPYC)GPU (e.g. H100)
Cores~64~16,896 (CUDA cores)
Cache per core~1MB L2~256KB L1/shared
Memory bandwidth~100 GB/s~3 TB/s
Compute (FP32)~5 TFLOPS~67 TFLOPS
Design goalMinimize latencyMaximize throughput
The key insight: A GPU achieves high throughput by hiding latency through massive parallelism. While one thread waits for memory, the GPU switches to another thread. You need thousands of independent threads to keep the GPU busy. This is why GPU programs are written differently than CPU programs.

2. Streaming Multiprocessor (SM)

An NVIDIA GPU consists of multiple Streaming Multiprocessors (SMs). An H100 has 132 SMs. Each SM is a self-contained compute unit with:

H100: 132 SMs × ~2048 threads/SM = ~270K threads in flight.

3. The Warp — the atomic unit of execution

Threads are grouped into warps of 32 threads. A warp is the smallest unit of execution on an NVIDIA GPU — all 32 threads in a warp execute the same instruction at the same time (SIMT).

Warp = 32 threads, executing in lockstep: Thread: 0 1 2 3 4 5 6 ... 31 │ │ │ │ │ │ │ │ ▼ ▼ ▼ ▼ ▼ ▼ ▼ ▼ [ LOAD A ] [ MUL ] [ STORE ] ─────────────────────────────────────→ time All 32 threads execute the SAME instruction simultaneously. If threads diverge (e.g., different branches in an if-statement), the GPU executes both paths sequentially — "warp divergence." Warp size = 32 on NVIDIA. On AMD, "wavefront" = 64.
Warp divergence kills performance. If half the warp takes the if branch and half takes the else, the GPU runs both sequentially — 50% of the warp is idle at any time. Minimize branch divergence within a warp.

4. Thread → Block → Grid hierarchy

NVIDIA's programming model has a three-level hierarchy:

Thread hierarchy: Grid ├── Block (0,0) │ ├── Warp 0: Thread 0..31 │ ├── Warp 1: Thread 32..63 │ ├── Warp 2: Thread 64..95 │ └── Warp 3: Thread 96..127 ├── Block (1,0) │ ├── Warp 0..3 │ ... ├── Block (0,1) │ ... └── ... (up to billions of blocks) Grid: the entire launch — all blocks Block: up to 1024 threads, can synchronize via __syncthreads() Warp: 32 threads, execute in lockstep Thread: the individual worker

Key design principle: Threads within a block can synchronize and share fast on-chip memory. Threads in different blocks cannot synchronize or communicate (except through global memory). This constraint is what makes the GPU scalable — blocks can be scheduled to any SM in any order.

5. SIMT execution model

NVIDIA calls its model SIMT (Single Instruction, Multiple Threads). It's like SIMD, but each thread has its own registers and can take different branches (though divergence is costly). The hardware manages the mapping of threads to lanes.

// All threads in a warp execute this line simultaneously
// But each thread has its own value of threadIdx.x

int tid = threadIdx.x + blockIdx.x * blockDim.x;

// Each thread loads from a different address
// — but the load instruction is the same for all
c[tid] = a[tid] + b[tid];

6. How a kernel launch works

// The triple-chevron syntax launches a kernel on the GPU:
my_kernel<<<numBlocks, threadsPerBlock>>>(arg1, arg2);

// Expanded form with more control:
my_kernel<<<gridDim, blockDim, sharedMem, stream>>>(args);

// gridDim:     number of blocks (dim3, can be 1D/2D/3D)
// blockDim:    threads per block (dim3)
// sharedMem:   bytes of shared memory per block (optional, default 0)
// stream:      CUDA stream for async execution (optional)
Kernel launch flow: CPU side: 1. Allocate GPU memory (cudaMalloc) 2. Copy input data to GPU (cudaMemcpy H→D) 3. Launch kernel: my_kernel<<<grid, block>>>(args) → CPU continues immediately (async!) 4. Wait for completion: cudaDeviceSynchronize() 5. Copy result back (cudaMemcpy D→H) GPU side: 1. Hardware schedules blocks onto SMs 2. Each block's threads are split into warps 3. Warp scheduler issues instructions 4. When all blocks finish, kernel is done

🎯 Chapter 00 Summary

GPUs trade latency for throughput via massive parallelism. The execution hierarchy is Grid → Block → Warp → Thread. A warp (32 threads) is the atomic unit — all threads execute the same instruction in lockstep. An SM is the physical compute unit with registers, shared memory, and tensor cores. Blocks can synchronize internally (__syncthreads), but different blocks cannot. Kernel launches are async — the CPU continues while the GPU runs.

🧪 Quick Check

You launch kernel<<<4, 256>>>(). How many threads total?

1,024 threads (4 blocks × 256 threads/block). These are split into 4 × 256 / 32 = 32 warps total. The GPU schedules these 4 blocks across available SMs — they may all run on one SM, or spread across multiple SMs.
