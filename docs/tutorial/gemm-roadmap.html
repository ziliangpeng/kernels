🔥 GEMM Mastery — From Beginner to Expert

A structured roadmap to deeply understanding matrix multiplication on GPUs · 6 dimensions · 5 phases · grounded in first-hand benchmarks

Why this page exists: GEMM looks like one operation — C = A × B — but there are dozens of named variants (SGEMM, split-K, WMMA, stream-K, GEMV, grouped GEMM...). This roadmap organizes them into a clear framework so you always know which dimension a new term belongs to, and what to learn next.

🧭 The 6-Dimension Framework

Every GEMM variant you'll ever encounter is a point in this 6-dimensional space. When you hear a new term, ask: which dimension?

D1 · Memory Hierarchy Ladder

The most important dimension. Each rung moves data reuse one level closer to the compute unit:

naive coalesced SMEM tiling 1D blocktile 2D blocktile vectorized load warp-tiled tensor core (WMMA/MMA)

Same GEMM, different level of the memory hierarchy doing the reuse. This is the ladder you've been climbing in the SGEMM project.

D2 · K-Axis Splitting

When M×N is too small to fill all SMs, you split along K to find more parallelism:

split-K stream-K persistent kernel

Critical for decode-shape FFN (small M) and skinny GEMMs.

D3 · Shape Regime

Different M/N/K ratios need fundamentally different kernel strategies:

GEMV (M=1) skinny GEMM (M<64) large/square GEMM batched GEMM grouped GEMM (MoE)

D4 · Precision

BLAS naming convention — same algorithm, different dtype:

SGEMM (FP32) DGEMM (FP64) HGEMM (FP16) BGEMM (BF16) FP8 GEMM (e4m3/e5m2) INT8 GEMM

FP8 adds a sub-dimension: scaling mode — tensorwise, rowwise, blockwise (1×128), each with different accuracy/perf trade-offs.

D5 · Hardware Instruction Layer

Which silicon unit does the math, and at what abstraction level:

CUDA cores (FFMA) WMMA (Volta–Ampere) mma.sync (Ampere+) WGMMA (Hopper) TMA (Hopper DMA) MFMA (AMD RDNA/CDNA) AITER (AMD GFX950)

Same operation, progressively lower-level control: WMMA = easy but rigid → mma.sync = fast but manual fragment layout → WGMMA = warpgroup-level, pairs with TMA.

D6 · Implementation Stack

Who writes the kernel — you, a compiler, or a library:

hand-written CUDA/HIP CUTLASS (C++ templates) Triton (compiler auto-tiles) cuBLAS / hipBLAS (black box) TinyGrad

CUTLASS makes D1×D2×D5 composable via templates. Triton hides D2 entirely (compiler decides). cuBLAS dispatches to hundreds of internal kernels by shape.

Key Insight

All GEMM variants answer the same question: "How do M×N×K arithmetic and data movement map onto the grid/block/warp/thread/tensor-core hardware structure?" Every term is a coordinate in this space. You don't need to memorize terms — you need the framework.

🗺️ Mastery Roadmap — Revised per GPT-5.6 Sol Review

Each phase targets a specific set of dimensions. Don't skip ahead — later phases build on intuitions from earlier ones.

Sol review (2026-08-28): the original roadmap was too GEMM-centric. Reordered: dense decode attention now comes BEFORE low precision / CUTLASS internals; the 90% cuBLAS exit gate is removed (67% is enough to move on); WGMMA/TMA is deferred until an attention/MLA kernel exists to justify it.
Phase 1 · Finish the FP32 Ladder [D1]

Complete what you started: warp-tiled → double buffering → (optional) WMMA

  • ✅ Steps 1–6: naive → vectorized — done, 6.6× over naive, 67% cuBLAS
  • ⬜ Step 7: Warp-tiled GEMM — assign each warp a sub-tile of the block tile. Introduces warp-level coordination via shuffle or SMEM.
  • ⬜ Step 8: Double buffering — ping-pong SMEM buffers to overlap next-tile load with current-tile compute. Sol: do this to prove you understand pipelining.
  • ⬜ Step 9: WMMA benchmark (light) — kernel already exists (matmul/matmul_wmma.cu). Benchmark it, compare, move on. Do NOT deep-dive tensor core yet — that comes back in Phase 4 with real justification.
Exit criterion (Sol-revised): large square SGEMM at 70–80% of cuBLAS under same math mode · warp-tiled + double-buffered each done by hand once · can use profiler to prove whether bandwidth-bound or compute-bound · correctness on non-divisible shapes and different strides/alignments. 90% single-shape target is removed — chasing it teaches architecture-specific tile hunting, not transferable skill.
Phase 2 · Dense Decode Primitives [D3 + new]

The bridge to attention: GEMV → reduction → online softmax → dense decode attention

  • ⬜ GEMV (M=1) — pure memory-bound, bandwidth saturation. This is ROADMAP 1.5.
  • ⬜ Warp-level reduction & shuffle — Sol: a missing frontier in the original roadmap. Reduction dependency is a core decode-attention concept.
  • ⬜ Online softmax — running max + running sum, stable rescaling. You have 8 variants in batch_softmax/; now connect it to attention.
  • ⬜ Contiguous KV decode attention — naive single-token attention with contiguous KV cache. QK dot products + PV accumulation.
  • ⬜ Fused dense decode attention — fuse QK, softmax, PV into one kernel. GQA/MQA support.
  • ⬜ RMSNorm + RoPE — the decode-block companions. You'll need them for the full forward pass anyway (ROADMAP Phase 6).
Exit criterion: a correct fused decode attention kernel, benchmarked across batch sizes, with profiler evidence of the memory-bound bottleneck.
Phase 3 · Irregular & Paged Kernels [D2 + D3]

Where the real DSA preparation begins

  • ⬜ Paged KV decode attention — indirect indexing, block table lookup, ragged sequence lengths. See docs/kb/paged-attention-tradeoff.md.
  • ⬜ Gather/scatter & pointer indirection — cache-line behaviour under indirect access. Sol-flagged missing frontier.
  • ⬜ Top-k / index selection — selection primitives, segmented reduction. The sparse-routing foundation.
  • ⬜ Split-K & multi-CTA reduction — split-K GEMM as a case study; then general multi-CTA reduction patterns.
  • ⬜ Flash Attention (algorithm level) — learn the online softmax recurrence, tiled QK/PV, stable rescaling, score-matrix avoidance. Do NOT chase FlashAttention-2/3 production performance here — that's a side quest. Mostly prefill material; decode path is what matters for DSA.
  • ⬜ Persistent kernel + load balancing — uneven selected-token counts, work stealing, variable work per block.
Exit criterion: paged decode attention correct on ragged batches; can reason about load balance when work per block is uneven.
Phase 4 · Tensor Core & Low Precision (need-driven) [D4 + D5]

Now WGMMA/TMA has a real consumer: your attention/MLA kernel

  • ⬜ Dense MLA decode reference — latent KV layout, decoupled RoPE component. The GQA→MQA→MLA data-structure evolution.
  • ⬜ FP16/BF16 with mma.sync — drop below WMMA to raw PTX; manual fragment layout. Depth first on ONE architecture before porting.
  • ⬜ FP8 GEMM with scaling modes — tensorwise → rowwise → blockwise (1×128). KB: docs/kb/fp8-gemm-*.md. Quantized KV + scale metadata reading in-kernel.
  • ⬜ Hopper WGMMA + TMA — only now, as tools to fix real bottlenecks in your MLA kernel. Not isolated instruction exercises.
  • ⬜ AMD port (optional) — after one architecture is deep, port to MI325X MFMA/AITER.
Exit criterion: correct FP8/quantized KV attention kernel on one architecture, with scaling-mode accuracy data from first-hand measurement.
Phase 5 · Sparse MLA & DSA [composite]

The end goal: assemble everything

  • ⬜ Extract DSA reference spec — Sol: kernel design is fully determined by latent dim, RoPE split, page size, selection granularity, index format, KV dtype, batch distribution. Extract data layout + math reference from the exact target implementation FIRST.
  • ⬜ Sparse selection + gather — top-k token selection, sparse QK, index generation ↔ consumer kernel interface.
  • ⬜ Stable sparse softmax — masked/sparse softmax stability, split-work reduction, zero selected blocks, duplicate indices, partial pages, tail dims, long context.
  • ⬜ Fused end-to-end DSA decode kernel — CUDA graph safety, workspace/allocator behaviour, end-to-end correctness oracle (not just per-op comparison).
  • ⬜ Profiler-driven optimization — HBM transactions, L2 hit rate, stall reasons, occupancy, wave utilization.
Exit criterion: a correct, profiler-validated DSA sparse MLA decode kernel written from scratch. The goal that started this journey.

Side branches (learn when needed, don't block the main line)

  • SWA / sliding window attention — Sol: it's a different sparsity pattern, NOT a DSA prerequisite. Receptive-field math is valuable but belongs on a side branch. (ROADMAP Phase 5 stays as-is, decoupled.)
  • CUTLASS / Triton internals — read on demand when a phase needs them (e.g. stream-K reading inside Phase 3), not as a standalone gate.
  • Grouped / batched GEMM, MoE dispatch — return when you work on MoE serving (ROADMAP 2.4).
  • DGEMM, exhaustive SGEMM autotuning, full cuBLAS dispatch reverse-engineering — explicitly deprioritized per Sol.

📖 Glossary — Every Term Mapped to a Dimension

When you encounter a GEMM term, find it here to see which dimension it belongs to:

TermDimOne-line definition
SGEMMD4Single-precision (FP32) GEMM — the BLAS name
DGEMMD4Double-precision (FP64) GEMM
HGEMMD4Half-precision (FP16) GEMM
BGEMMD4BF16 GEMM
GEMVD3Matrix-vector multiply (M=1), memory-bound
naive GEMMD1One thread per output element, no reuse
coalesced GEMMD1Fix warp-to-memory mapping for coalesced access
SMEM tilingD1Load a tile of A+B into shared memory, reuse across block
1D blocktileD1Each thread computes multiple outputs; register reuse of B
2D blocktileD1Outer product: register reuse of both A and B (TM×TN)
vectorized loadD1Use float4/float2 to load 4/2 elements per instruction
warp-tiledD1Each warp owns a sub-tile; warp-level coordination
double bufferingD1Ping-pong SMEM: load next tile while computing current
WMMAD5Warp Matrix Multiply Accumulate — Volta-era tensor core API (nvcuda::wmma)
mma.syncD5PTX-level tensor core instruction, more control than WMMA
WGMMAD5Warpgroup MMA — Hopper, 4 warps cooperate
TMAD5Tensor Memory Accelerator — Hopper async DMA to SMEM
MFMAD5Matrix Fused Multiply-Add — AMD's tensor core equivalent
AITERD5AMD GFX950 (MI350X) matrix instruction library
split-KD2Split K into S chunks, each block computes partial C, then reduce
stream-KD2Dynamic K-chunk scheduling; fixes split-K quantization waste
persistent kernelD2Launch #SMs blocks, each processes multiple tiles until done
batched GEMMD3N independent GEMMs of same shape, one launch
grouped GEMMD3Variable-shape GEMMs packed into one launch (MoE)
CUTLASSD6NVIDIA's open-source C++ template GEMM framework
cuBLASD6NVIDIA's closed-source BLAS library
tensorwise scalingD4FP8: one scale factor for entire tensor
rowwise scalingD4FP8: one scale factor per row
blockwise (1×128) scalingD4FP8: one scale per 1×128 block ( finest granularity )
epilogue fusionD1Fuse bias/activation into GEMM epilogue, save a memory round-trip
bank conflictD1SMEM access pattern where multiple threads hit same bank → serialization
cp.asyncD1Async global→SMEM copy (Ampere+), enables pipelining without double buffer
occupancyD1Ratio of resident warps to max warps per SM — affected by registers/SMEM
arithmetic intensityD1FLOPs per byte loaded — determines compute-bound vs memory-bound
rooflineD1Visual model: peak FLOPS vs bandwidth limit, by arithmetic intensity
Not on this list? Every GEMM term maps to one of the 6 dimensions. If you can't place it, it's likely a synonym or a combination. Example: "ping-pong scheduling" = double buffering (D1). "hopper GEMM" = WGMMA + TMA (D5).

How to use this roadmap

  1. You are here: Phase 1, step 7 (warp-tiled). 6 of 10 steps done.
  2. Read dimensions first. When you encounter a new term, place it in D1–D6 before diving into implementation.
  3. Always benchmark. Every step should produce a TFLOPS number and a "% of cuBLAS" comparison. No theory without measurement.
  4. Write the kernel yourself. Reading CUTLASS source is Phase 4. In Phases 1–3, write from scratch — the intuitions only come from doing.
  5. One step at a time. Don't jump to FP8 until FP32 ladder is done. Don't do split-K until you've felt the occupancy limit yourself.
