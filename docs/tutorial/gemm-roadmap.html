🔥 GEMM Mastery — From Beginner to Expert

A structured roadmap to deeply understanding matrix multiplication on GPUs · 6 dimensions · 5 phases · grounded in first-hand benchmarks

Why this page exists: GEMM looks like one operation — C = A × B — but there are dozens of named variants (SGEMM, split-K, WMMA, stream-K, GEMV, grouped GEMM...). This roadmap organizes them into a clear framework so you always know which dimension a new term belongs to, and what to learn next.

🧭 The 6-Dimension Framework

Every GEMM variant you'll ever encounter is a point in this 6-dimensional space. When you hear a new term, ask: which dimension?

D1 · Memory Hierarchy Ladder

The most important dimension. Each rung moves data reuse one level closer to the compute unit:

naive coalesced SMEM tiling 1D blocktile 2D blocktile vectorized load warp-tiled tensor core (WMMA/MMA)

Same GEMM, different level of the memory hierarchy doing the reuse. This is the ladder you've been climbing in the SGEMM project.

D2 · K-Axis Splitting

When M×N is too small to fill all SMs, you split along K to find more parallelism:

split-K stream-K persistent kernel

Critical for decode-shape FFN (small M) and skinny GEMMs.

D3 · Shape Regime

Different M/N/K ratios need fundamentally different kernel strategies:

GEMV (M=1) skinny GEMM (M<64) large/square GEMM batched GEMM grouped GEMM (MoE)

D4 · Precision

BLAS naming convention — same algorithm, different dtype:

SGEMM (FP32) DGEMM (FP64) HGEMM (FP16) BGEMM (BF16) FP8 GEMM (e4m3/e5m2) INT8 GEMM

FP8 adds a sub-dimension: scaling mode — tensorwise, rowwise, blockwise (1×128), each with different accuracy/perf trade-offs.

D5 · Hardware Instruction Layer

Which silicon unit does the math, and at what abstraction level:

CUDA cores (FFMA) WMMA (Volta–Ampere) mma.sync (Ampere+) WGMMA (Hopper) TMA (Hopper DMA) MFMA (AMD RDNA/CDNA) AITER (AMD GFX950)

Same operation, progressively lower-level control: WMMA = easy but rigid → mma.sync = fast but manual fragment layout → WGMMA = warpgroup-level, pairs with TMA.

D6 · Implementation Stack

Who writes the kernel — you, a compiler, or a library:

hand-written CUDA/HIP CUTLASS (C++ templates) Triton (compiler auto-tiles) cuBLAS / hipBLAS (black box) TinyGrad

CUTLASS makes D1×D2×D5 composable via templates. Triton hides D2 entirely (compiler decides). cuBLAS dispatches to hundreds of internal kernels by shape.

Key Insight

All GEMM variants answer the same question: "How do M×N×K arithmetic and data movement map onto the grid/block/warp/thread/tensor-core hardware structure?" Every term is a coordinate in this space. You don't need to memorize terms — you need the framework.

🗺️ 5-Phase Mastery Roadmap

Each phase targets a specific set of dimensions. Don't skip ahead — later phases build on intuitions from earlier ones.

Phase 1 · Finish the FP32 Ladder [D1]

Complete what you started: warp-tiled → tensor core → double buffer

  • ✅ Steps 1–6: naive → vectorized — done, 6.6× over naive, 67% cuBLAS
  • ⬜ Step 7: Warp-tiled GEMM — assign each warp a sub-tile of the block tile. Introduces warp-level coordination via shuffle or SMEM. This is the bridge between 2D blocktile and tensor core.
  • ⬜ Step 8: Tensor Core GEMM (WMMA) — use nvcuda::wmma to do 16×16 matrix multiply in hardware. Target: match or beat cuBLAS FP32. Kernel already exists at matmul/matmul_wmma.cu — benchmark it.
  • ⬜ Step 9: Double buffering — ping-pong SMEM buffers to overlap next-tile load with current-tile compute. Hides memory latency.
  • ⬜ Step 10: Autotune the full ladder — sweep all tile sizes for steps 7–9. Document the Pareto frontier. Compare against your H100 first-hand results.
Exit criterion: hand-written FP32 GEMM reaches ≥90% of cuBLAS FP32 on a 4096² shape.
Phase 2 · Low Precision & Hardware Instructions [D4 + D5]

FP16/BF16 → FP8 → mma.sync → cross-vendor (AMD MFMA)

  • ⬜ FP16/BF16 GEMM with tensor core — switch dtype, use WMMA FP16 fragment. Study accumulator precision (FP32 accum). Read your KB note: docs/kb/gemm-fp16-vs-bf16.md.
  • ⬜ FP8 GEMM (e4m3) — the frontier. Scaling modes: tensorwise → rowwise → blockwise (1×128). Read your KB notes: docs/kb/fp8-gemm-*.md (5 files). Benchmark on H100 (DeepGEMM) and MI325X (aiter).
  • ⬜ mma.sync (PTX-level) — drop down from WMMA to raw mma.sync instructions. Manually manage fragment layout. This is what CUTLASS uses internally.
  • ⬜ AMD MFMA — port GEMM to HIP. Use MFMA instructions on MI325X (GFX950). Compare instruction shape: NVIDIA 16×16 vs AMD 16×16/32×32/4×64. Read docs/kb/hardware-mi325x.md.
Exit criterion: can write a correct FP8 GEMM on both H100 and MI325X, and explain the scaling-mode trade-offs from first-hand data.
Phase 3 · Shape-Dependent GEMM [D3 + D2]

GEMV → skinny GEMM → split-K → stream-K → batched/grouped

  • ⬜ GEMV (M=1) — the decode case. Pure memory-bound. Each weight read once. Optimize for bandwidth, not FLOPS. This is ROADMAP 1.5.
  • ⬜ Skinny GEMM sweep (M=1,8,32,128,512,2048) — benchmark same kernel across shapes. Find crossover points: when does split-K help? When does small-tile win? This is ROADMAP 2.2.
  • ⬜ Split-K GEMM — split K into S chunks, S blocks compute partial C, atomic add or 2nd-kernel reduce. Measure: when does the parallelism gain outweigh the reduction overhead?
  • ⬜ Stream-K GEMM — scheduler-driven K-chunk assignment. Read the CUTLASS stream-K paper/code. Understand how it fixes split-K's quantization waste.
  • ⬜ Batched & Grouped GEMM — strided batched (same shape, N independent GEMMs) and grouped (variable shapes, MoE dispatch). This is ROADMAP 2.4.
Exit criterion: can pick the right K-splitting strategy for any M/N/K shape and justify it with data.
Phase 4 · CUTLASS & Library Internals [D6]

Read the source of production GEMM libraries

  • ⬜ CUTLASS architecture — understand the template combinator: ThreadblockShape × WarpShape × InstructionShape × Epilogue. Map each template parameter to D1/D2/D5.
  • ⬜ CUTLASS stream-K implementation — read the actual stream-K scheduler in CUTLASS. Trace how work is dynamically assigned.
  • ⬜ cuBLAS dispatch logic — understand how cuBLAS picks among hundreds of internal kernels by shape/dtype. Use Nsight to see which kernel cuBLAS actually calls.
  • ⬜ Triton GEMM internals — read Triton's tl.dot lowering. Understand how the compiler auto-tiles and auto-pipelines. Compare to your hand-written tiles.
Exit criterion: can read a CUTLASS kernel definition and predict its tile/pipeline/split strategy without running it.
Phase 5 · Advanced & Specialized GEMM [D1+D2+D5]

Hopper WGMMA · fused epilogue · quantized · persistent

  • ⬜ Hopper: WGMMA + TMA — warpgroup-level MMA (4 warps cooperate). TMA does async DMA to SMEM without thread involvement. The cutting edge of NVIDIA GEMM.
  • ⬜ Fused GEMM (GEMM+SiLU, GEMM+bias) — epilogue fusion. ROADMAP 2.3. Understand why fusing saves a memory round-trip.
  • ⬜ Quantized GEMM (INT8, weight-only) — dequantize in-kernel, mixed precision. Relevance: LLM serving with INT4/INT8 weights.
  • ⬜ GEMM for attention (QK^T, SV) — how GEMM shapes change in attention vs FFN. Bridge to FlashAttention (ROADMAP Phase 3).
  • ⬜ Persistent kernel + software scheduling — launch exactly #SMs blocks, each processes multiple tiles. Avoids launch overhead, enables fine-grained work stealing.
Exit criterion: can design a GEMM kernel for a novel hardware target or unusual shape from first principles, and predict its performance.

How to use this roadmap

  1. You are here: Phase 1, step 7 (warp-tiled). 6 of 10 steps done.
  2. Read dimensions first. When you encounter a new term, place it in D1–D6 before diving into implementation.
  3. Always benchmark. Every step should produce a TFLOPS number and a "% of cuBLAS" comparison. No theory without measurement.
  4. Write the kernel yourself. Reading CUTLASS source is Phase 4. In Phases 1–3, write from scratch — the intuitions only come from doing.
  5. One step at a time. Don't jump to FP8 until FP32 ladder is done. Don't do split-K until you've felt the occupancy limit yourself.
