1. The problem: matrix multiplication

GEMM (General Matrix Multiply) is C = A × B where A is M×K, B is K×N, C is M×N. It's the most important kernel in deep learning — every Linear layer is a GEMM. Optimizing GEMM is the canonical GPU programming exercise.

GEMM: C = A × B A (M×K) B (K×N) C (M×N) ┌─────┐ ┌─────┐ ┌─────┐ │a a a│ × │b b b│ = │c c c│ │a a a│ │b b b│ │c c c│ │a a a│ │b b b│ │c c c│ └─────┘ └─────┘ └─────┘ C[i][j] = Σ A[i][k] * B[k][j] for k=0..K-1 Each output element needs K multiply-adds. Total: M*N*K FLOPs (2× that if counting mul+add separately)

2. Naive kernel — one thread per output

The simplest approach: each thread computes one element of C by iterating over K.

// Naive GEMM: C = A × B
// A: M×K (row-major), B: K×N (row-major), C: M×N (row-major)
__global__ void gemm_naive(const float* A, const float* B, float* C,
                           int M, int N, int K) {
    // Each thread computes C[row][col]
    int row = blockIdx.y * blockDim.y + threadIdx.y;
    int col = blockIdx.x * blockDim.x + threadIdx.x;

    if (row < M && col < N) {
        float sum = 0.0f;
        for (int k = 0; k < K; k++) {
            sum += A[row * K + k] * B[k * N + col];
        }
        C[row * N + col] = sum;
    }
}

// Launch config
dim3 block(16, 16);
dim3 grid((N + 15) / 16, (M + 15) / 16);
gemm_naive<<<grid, block>>>(d_A, d_B, d_C, M, N, K);

3. Bottleneck analysis

This kernel is extremely slow. Let's see why.

For M=N=K=4096:

  • Each thread does K=4096 iterations, each loading 2 floats (A and B) = 8 bytes per iteration
  • Each output element loads 2 × K × 4 = 32KB from global memory
  • Total global memory loaded: M × N × 2 × K × 4 = 4096³ × 8 = 549 GB
  • But the actual data is only (M×K + K×N) × 4 = 2 × 4096² × 4 = 134 MB
  • Each byte is loaded ~4000 times! This is a 4000× amplification.
Naive GEMM memory traffic: Thread computing C[0][0] loads: A[0][0..4095] → 4096 floats from row 0 of A B[0..4095][0] → 4096 floats from col 0 of B Thread computing C[0][1] loads: A[0][0..4095] → SAME data, loaded AGAIN B[0..4095][1] → different column Thread computing C[1][0] loads: A[1][0..4095] → different row B[0..4095][0] → SAME data, loaded AGAIN → Massive redundancy. Each A row is loaded N times, each B column M times.

4. What's wrong and how to fix it

The problem: Every thread independently loads A and B from global memory. There's massive redundancy — the same A row is loaded by all N threads in that row, and the same B column is loaded by all M threads in that column.

The fix is shared memory tiling (chapter 08): load a tile of A and B into shared memory once, then all threads in the block reuse it from fast SMEM instead of going to global memory. But first, chapter 07 fixes a simpler issue — the access pattern.

🎯 Chapter 06 Summary

Naive GEMM: one thread per output element, looping over K. Each thread loads 2×K floats from global memory — massive redundancy (each A row loaded N times, each B column loaded M times). Memory amplification ~K×. Result: ~0.5 TFLOPS vs 67 TFLOPS peak on H100. The fix is shared memory tiling to reuse loaded data.

🧪 Quick Check

For M=N=K=4096 FP32 GEMM, how much data does the naive kernel load from global memory?

M × N × 2 × K × 4 bytes = 4096 × 4096 × 2 × 4096 × 4 = 549 GB. The actual matrices are only (M×K + K×N) × 4 = 134 MB. So each byte is loaded ~4000 times. This is why naive GEMM achieves <1% of peak — it's drowning in redundant memory traffic. Shared memory tiling (chapter 08) reduces this to ~1× amplification.
