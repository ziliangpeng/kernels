1. Problem: one float per load instruction

Each load instruction loads 4 bytes (one float). But the memory bus is 128 bytes wide. To fill a 128-byte cache line, you need 32 separate load instructions from 32 threads. Even with coalescing, each thread issues one load per element.

Without vectorization: Thread 0: load 4B → 1 instruction, 4 bytes Thread 1: load 4B → 1 instruction, 4 bytes ... Thread 31: load 4B → 1 instruction, 4 bytes Total: 32 instructions, 128 bytes (coalesced into 1 transaction) With float4 vectorized load: Thread 0: load 16B → 1 instruction, 16 bytes (4 floats!) Thread 1: load 16B → 1 instruction, 16 bytes ... Thread 7: load 16B → 1 instruction, 16 bytes Total: 8 instructions, 128 bytes (coalesced into 1 transaction) → 4× fewer instructions for the same data!

2. float4 — load 4 floats at once

// float4 is a built-in CUDA type: 4 contiguous floats
// Reinterpret a float* as float4* and load 4 at once

__global__ void load_vectorized(const float* in, float* out, int n) {
    int tid = blockIdx.x * blockDim.x + threadIdx.x;
    int idx = tid * 4;  // each thread handles 4 elements

    if (idx + 3 < n) {
        // Cast to float4* and load — one instruction, 4 floats
        float4 data = *reinterpret_cast<const float4*>(&in[idx]);

        // Access individual elements
        out[idx]     = data.x;
        out[idx + 1] = data.y;
        out[idx + 2] = data.z;
        out[idx + 3] = data.w;
    }
}

3. Alignment requirement

float4 loads require 16-byte alignment. The address must be a multiple of 16. If not, you get a crash or undefined behavior. cudaMalloc returns 256-byte-aligned pointers, so allocations are fine. But if you're loading from an offset, make sure offset % 4 == 0.

4. Vectorized loads in GEMM

In the SMEM cooperative load phase, each thread loads one float. With float4, each thread loads 4 floats — 4× fewer instructions, 4× less overhead.

// Before: each thread loads 1 float to SMEM
As[ty][tx] = A[row * K + kt + threadIdx.x];

// After: each thread loads 4 floats (float4) to SMEM
float4 a4 = *reinterpret_cast<const float4*>(&A[row * K + kt + threadIdx.x * 4]);
As[ty][tx * 4 + 0] = a4.x;
As[ty][tx * 4 + 1] = a4.y;
As[ty][tx * 4 + 2] = a4.z;
As[ty][tx * 4 + 3] = a4.w;

🧪 Quick Check

Why does float4 give only ~20% improvement instead of 4×?

Because the GEMM kernel is not purely memory-bound — it's a mix of compute (mul-add) and memory. float4 reduces the load instruction count by 4×, but the total memory bytes are the same (the cache line is still 128B). The 20% gain comes from reduced instruction issue overhead, not from more bandwidth. The compute portion (mul-adds in the inner loop) is unchanged.
