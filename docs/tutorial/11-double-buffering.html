1. Problem: sequential load → compute

In the tiled GEMM, each tile iteration is: load SMEM → syncthreads → compute → syncthreads. The load and compute are sequential — while computing, the memory bus is idle; while loading, the compute units are idle.

Without double buffering (sequential): Time → ┌──────────┐ ┌──────────┐ ┌──────────┐ │ Load │ sync │ Compute │ sync │ Load │ ... │ tile 0 │ │ tile 0 │ │ tile 1 │ └──────────┘ └──────────┘ └──────────┘ ← memory busy → ← compute busy → ← memory busy → Memory and compute are NEVER active at the same time!

2. Double buffering — overlap load and compute

Use two SMEM buffers (ping-pong). While computing from buffer A, load the next tile into buffer B. Then swap.

With double buffering (overlapped): Time → ┌──────────┐──────────┐──────────┐──────────┐ │ Load │ Load │ Load │ Load │ ← memory always busy │ tile 0 │ tile 1 │ tile 2 │ tile 3 │ └──────────┴──────────┴──────────┴──────────┘ ┌──────────┐──────────┐──────────┐ │ Compute │ Compute │ Compute │ ← compute always busy │ tile 0 │ tile 1 │ tile 2 │ └──────────┴──────────┴──────────┘ Load and compute overlap → ~2× speedup for memory-bound phases

3. Double-buffered GEMM

__global__ void gemm_double_buf(const float* A, const float* B,
                                   float* C, int M, int N, int K) {
    __shared__ float As[2][BM][BK];  // TWO buffers (ping-pong)
    __shared__ float Bs[2][BK][BN];

    int buf = 0;  // current buffer index

    // Pre-load tile 0 into buffer 0
    load_tile(A, B, As[0], Bs[0], 0);
    __syncthreads();

    for (int kt = 0; kt < K - BK; kt += BK) {
        // Load NEXT tile into the OTHER buffer (async, overlapped)
        int next_buf = 1 - buf;
        load_tile(A, B, As[next_buf], Bs[next_buf], kt + BK);

        // Compute from CURRENT buffer
        compute_tile(As[buf], Bs[buf], regC);

        // Wait for both load and compute to finish
        __syncthreads();
        buf = next_buf;
    }

    // Compute the last tile
    compute_tile(As[buf], Bs[buf], regC);
    __syncthreads();
}

4. Measured improvement

Thread-tiled + float4~10-12baseline

15% improvement — the load and compute phases overlap, hiding the memory latency behind compute. The improvement depends on the load/compute ratio: if your kernel is 50/50, double buffering gives ~2×; if it's 90% compute, you get ~10%.

5. Modern alternative: cp.async

On Ampere+ (sm_80+), use cp.async for true async global→SMEM copies without going through registers. Combined with cp.async.commit_group/wait_group, this gives fine-grained pipelining without double SMEM allocation.

// Modern async copy (Ampere+)
asm("cp.async.cg.shared.global [%0], [%1], 16;"
    :: "r"(smem_addr), "l"(global_addr));

cp_async_commit_group();  // mark a group of copies
cp_async_wait_group(0);   // wait for N-1 groups ago
__syncthreads();

🧪 Quick Check

Why does double buffering only give ~15% improvement, not ~2×?

Because by this point in the optimization ladder, the kernel is already compute-bound, not memory-bound. Double buffering overlaps load with compute, but if compute takes 80% of the time and load 20%, the overlap only saves ~15% (you can hide most of the 20% load behind the 80% compute). If the kernel were 50/50, you'd get closer to 2×. The more compute-heavy the kernel, the less double buffering helps.
