1. What is occupancy?

Occupancy = the ratio of active warps per SM to the maximum possible warps per SM. High occupancy means the SM has lots of warps to schedule, which helps hide memory latency.

// Theoretical max warps per SM (H100):
//   2048 threads / 32 = 64 warps

// If your kernel uses 256 threads/block and 2 blocks fit per SM:
//   2 blocks × 256 threads = 512 threads = 16 warps
//   Occupancy = 16 / 64 = 25%

// If your kernel uses 128 threads/block and 8 blocks fit:
//   8 × 128 = 1024 threads = 32 warps
//   Occupancy = 32 / 64 = 50%

2. What limits occupancy?

ResourceHow it limitsMitigation
Registers per threadMore regs → fewer threads fit in SM's register fileReduce register usage, use __launch_bounds__
Shared memory per blockMore SMEM → fewer blocks fit in SM's SMEMReduce tile size, use dynamic SMEM
Threads per blockMax 1024, but large blocks limit concurrent blocksUse 128-256 threads per block
Blocks per SMHard limit (24-32 on H100)Don't launch too many tiny blocks

3. Occupancy calculation example

H100 SM resources: Registers: 65,536 per SM Shared memory: 228KB per SM Max threads: 2048 per SM Max blocks: 32 per SM Kernel: 256 threads/block, 32 registers/thread, 8KB SMEM/block Register limit: 65536 / (256 × 32) = 8 blocks → 8 × 256 = 2048 threads ✓ SMEM limit: 228KB / 8KB = 28 blocks → but max 32 → 28 blocks Thread limit: 2048 / 256 = 8 blocks Block limit: 32 (hard cap) Actual: min(8, 28, 8, 32) = 8 blocks → 8 × 256 = 2048 threads Occupancy: 2048 / 2048 = 100% ✓ Now if kernel uses 64 regs/thread instead: Register limit: 65536 / (256 × 64) = 4 blocks → 4 × 256 = 1024 threads Occupancy: 1024 / 2048 = 50% — register pressure halved occupancy!

4. Occupancy vs register pressure tradeoff

More registers per thread = fewer threads = lower occupancy. But more registers can mean less spilling and faster per-thread execution. The optimal point isn't always 100% occupancy — sometimes 50% occupancy with more registers is faster. Profile to find the sweet spot. 
// Control register usage with __launch_bounds__
__global__ void __launch_bounds__(256, 8) my_kernel() {
    // 256 threads/block, target 8 blocks/SM
    // Compiler will limit registers to fit this
}

// Check occupancy with CUDA API:
int maxActiveBlocks;
cudaOccupancyMaxActiveBlocksPerMultiprocessor(&maxActiveBlocks, my_kernel, 256, 0);
float occupancy = (float)maxActiveBlocks * 256 / 2048;

5. The roofline model

Roofline: where is your kernel bottlenecked? Performance (FLOPS) ↑ │ compute ceiling (e.g. 67 TFLOPS FP32) │ ╱───────────────── │ ╱ │ ╱ ← memory bandwidth ceiling │ ╱ (slope = 3 TB/s = 3e12 B/s) │ ╱ │ ╱ │ ╱ │ ╱ └──────────────────→ Arithmetic intensity (FLOPS/byte) If your kernel is below the memory ceiling line → memory-bound If your kernel is at the compute ceiling → compute-bound The "knee" is where the two ceilings meet.

Arithmetic intensity = FLOPS performed / bytes loaded. GEMM has high intensity (each byte is reused many times). Vector add has low intensity (each byte is used once). High-intensity kernels benefit from compute optimization; low-intensity kernels are limited by memory bandwidth.

🎯 Chapter 05 Summary

Occupancy = active warps / max warps per SM. Limited by registers, shared memory, and block/thread caps. Calculate: min(register_limit, smem_limit, thread_limit, block_limit). Higher occupancy hides latency better, but more registers per thread (lower occupancy) can be faster if it prevents spilling. Use the roofline model to determine if your kernel is memory-bound or compute-bound.

🧪 Quick Check

Your kernel uses 128 threads/block and 40 registers/thread on H100 (65536 regs/SM). How many blocks fit per SM?

65536 / (128 × 40) = 12.8 → 12 blocks (round down). 12 blocks × 128 threads = 1536 threads. Occupancy = 1536 / 2048 = 75%. If you reduce to 32 regs/thread: 65536 / (128 × 32) = 16 blocks → 16 × 128 = 2048 → 100% occupancy. But check if the extra register spills hurt performance more than the occupancy helps.
